# PR 01a / PR 01b architecture

Next.js App Router runs server components and Node route handlers. Interactive forms use shadcn/ui primitives and Tailwind CSS variables. Geist is self-hosted. UI content and layout are Harvest-owned; reference screenshots provide visual language only. The responsive dashboard shell uses the official shadcn floating sidebar, with a focus-managed sheet below 1024px, a full-width content area with compact 16px/24px gutters (see the ADR 0004 supersession note), and only the implemented workspace, CRM, files and appearance destinations.

Better Auth stores users, sessions, verification hashes and database-backed rate limits through its Drizzle adapter. Email OTP is the only exposed sign-in mechanism: six digits, ten-minute expiry, five wrong attempts, keyed SHA-256 hash, and an atomic normalized-email resend cooldown of 60 seconds, plus rolling five-per-hour and twenty-per-day issuance limits. OTP hashes bind the normalized recipient and sign-in purpose; failed delivery releases only its own reservation. HTTP/IP limits also persist in Postgres. Only code-send, code-sign-in, session-read and sign-out routes are exposed. Unused Better Auth account columns exist for adapter compatibility; password login and OAuth are disabled. Request-scoped delivery awaiting surfaces safe errors instead of claiming success when Resend fails.

Workspace creation, member addition and role change are centralized services. Routes verify Better Auth sessions, enforce same-origin mutations, strictly validate input and pass only the verified session user ID to services. A requested workspace ID is a lookup hint. `withUser` starts a transaction and sets the verified user context. `withTenant` looks up that user's membership under RLS, derives the tenant from the stored membership, sets `app.tenant_id` locally, then locks and rechecks membership and permission before invoking domain code. Parameterized `set_config(..., true)` has SET LOCAL semantics and resets on commit/rollback. Membership locks prevent revocation racing an authorized operation. User/tenant state is never stored on a pooled session outside its transaction.

`workspace_members` permits users to discover their own memberships only while no tenant context is selected. After selection all memberships are tenant-qualified. All other tenant reads require tenant context. Every tenant-owned row carries `tenant_id`; workspace IDs are tenant IDs, membership keys are composite, and audit indexes include tenant and time. Users/auth records and the fixed role catalog are global infrastructure. No client context/header is trusted as authorization. RLS is defense in depth against missing tenant filters; arbitrary SQL execution or a compromised application server is outside this trust boundary because PostgreSQL custom settings are settable by the application role.

The SQL-created `harvest_app` role owns no tables, has no elevated memberships, and has neither superuser nor BYPASSRLS. All tenant tables enable and force RLS. Audit grants permit insert/select only; triggers reject deletion/truncation and all updates except the erasure definer’s exact contact-audit unlinking transformation. Tenant mutation audit events share the same transaction as the business write and contain IDs/role changes, never codes, tokens, email bodies or secrets. Sign-in creates a global audit event associated with the verified user. Contact create/update, consent recording and workspace appearance updates append audit events in the same transaction. Contact details and consent evidence never enter audit metadata.

The runtime uses a small connection pool. Neon uses the official WebSocket pool for interactive transactions, and local Postgres uses `pg`. Migrations use the unpooled owner URL, run only in CI by default, and have an explicit metadata-checked dev-verification command authorized for this task. Staging/prod are never migrated by the PR workflow. Database pool/auth/route failures produce redacted event names; responses expose safe actionable errors. There is no provider error-body or query logging.

Roles: owner/admin may manage members, workspace settings and contact erasure; owner/admin/member may write contacts and record consent; viewers may only read contacts and settings. Unknown roles fail closed. Only owners can grant/revoke ownership; a serialized check preserves the final owner. Member targets must already have signed in. No invitation email flow is included. Dodo is an unavailable adapter contract and environment-variable name only.


## Contacts and consent

`contacts` uses `(tenant_id, id)` as its primary key and has a `(tenant_id, name, id)` listing index. The list is searched on the server by name or identifier and paginated at 20 rows with stable name/ID ordering. All reads, joins, updates and child lookups are explicitly tenant-qualified in addition to RLS. No tenant data is placed in a shared Next cache.

`contact_identifiers` uses composite tenant/contact foreign keys and unique `(tenant_id, kind, normalized_value)` identity. This slice accepts one email, phone and social handle per contact. Email is case folded; international phone separators are removed without guessing a country; social handles are case folded and their optional leading @ is removed for identity. The same identity may exist independently in another tenant. Duplicate identities produce a safe 409 and roll back the entire write. Contacts are never automatically merged.

`contact_consents` records channel, status, controlled purpose/wording version, source/evidence, the verified recording actor and separate occurrence/recording timestamps. Composite foreign keys prevent linking a child to a foreign tenant contact. Creating a contact records no consent. Recording time is always assigned by the database insert trigger, overriding client-supplied values. History uses descending recording time, then occurrence time and ID. Effective consent is computed per purpose/channel: any withdrawal remains effective unless a grant is strictly later on both clocks. Backdated grants and equal timestamps never clear an outstanding withdrawal. The marketing summary uses that same result, with timestamp comparisons performed in PostgreSQL to preserve microsecond precision. Occurrence is bounded to recording time plus five minutes in PostgreSQL and to the current clock plus five minutes in Zod; history preserves all purposes. Two events in one transaction share PostgreSQL’s transaction-start recording timestamp; the withdrawal wins the tie. History labels grants that did not override an outstanding withdrawal. Runtime privileges forbid UPDATE/DELETE/TRUNCATE. Withdrawal appends an event.

Owner/admin erasure anonymizes the contact and detaches/redacts its ledger entries through a single audited SQL function; facts remain immutable. The application role receives EXECUTE only, while a fixed security-definer function rechecks context and membership, locks the parent, clears contact text, deletes identifiers, removes actor/channel links and free text from consent, re-keys anonymous event IDs, and repoints proofs to a new random parent tombstone ID. The retained contact is re-keyed and its created/updated/erased timestamps are truncated to UTC days, so contacts, consents and audits retain no original contact ID. The owner-only contact guard permits exactly this re-key and coarsening; the composite consent FK is deferred only during the operation and checked immediately afterwards. Shared xmin/date joins can associate anonymous rows but cannot recover the original ID. It truncates recording, occurrence and redaction timestamps to UTC days, clamping occurrence clock skew across midnight to the recording day. The guard allows only this exact coarsening, preserving the consent facts. Erasure also nulls contact/consent audit targets and clears their metadata, including channel, consent IDs and status, before re-keying the ledger. The audit guard permits only that transformation by the erasure definer after the contact is erased in the matching tenant context; event ID, tenant, actor, action and creation time remain immutable. The retained erasure event has no contact target or metadata. Amended, undeployed migration 0008 also re-keys older tombstones and scrubs their contact-targeted audits; previously detached proofs remain detached, and old consent-ID-only audit references are outside that backfill. No deployed data exists. Original-ID requests return 404 after erasure. No caller-set flag bypasses ledger or audit protection, FORCE RLS and tenant WITH CHECK policies remain active, and contact tombstones cannot be reactivated. Audit failure rolls both ledger redaction and audit unlinking back. [Follow-up contracts and evidence](acceptance/pr01b-followups.md) supersede round 3’s recording-order and audit-retention statements. There is no marketing delivery integration in this slice.

The new tables enable and force RLS and grant only the runtime operations required by the services. Integration checks use the actual restricted application role, exercise missing/foreign tenant context, audit rollback, normalized identity collisions, viewer denial, and same-physical-backend context reset on commit and rollback. Disposable local PostgreSQL applies the migrations twice to prove idempotence. The inherited CI workflow also migrates a temporary Neon CI branch; staging validation remains a separate release check and no long-lived environment is migrated by this PR.

## Appearance and routing

`workspaces.brand_theme` defaults to Harvest and has a database check restricting values to Harvest/Studio. Only owner/admin services may change it, with an atomic audit event. User localStorage `harvest-brand-theme` wins over the workspace setting; absence or invalid values fall back to the workspace and then Harvest. Color mode is independent, stored as `harvest-color-mode`, with system preference when unset. Storage denial is handled, and a transient in-page choice still works.

A synchronous head script initializes `data-brand-theme` and `data-theme` before body paint. A minimal Next proxy overwrites a route-hint header from the URL; the root layout resolves the workspace brand only through a verified session and membership. The hint confers no authority. Client navigation reapplies the selected workspace default in a layout effect, and cross-tab storage/system-mode changes update the same semantic tokens. All business UI reads CSS variables rather than brand names. Inter and Geist are self-hosted; gold actions use dark text and an accessible lighter hover. See ADR 0004.

Private workspace pages use `/workspaces/:tenantId/contacts` and `/appearance` on the shared application domain. No per-tenant subdomain, DNS, public contact route or cross-workspace contact directory is introduced. PRD 9.1's globally discoverable content is future scope and does not change private contact/member/settings isolation.

## CRM people and companies (CRM-01/02)

People are the existing `contacts`; there is no second person table. `companies` and `contact_company_links` follow the same tenancy rules: composite `(tenant_id, …)` keys, forced RLS, transaction-local tenant context and explicit tenant predicates in every query. Links reference both parents through composite tenant FKs. A trigger requires a live contact and binds provenance to `app.user_id`. A partial unique index keeps one primary company per person. Company domains are normalized and unique per tenant. Names are never identities, and same-name records appear only as suggestions. Contacts and companies carry a `version` for optimistic inline edits (409 `stale`). CRM activity is read from the append-only audit ledger. Link events are `contact.*` actions targeting the person, so the erasure definer unlinks them, and erasure deletes the person's links before re-keying. Screens live at `/workspaces/:tenantId/crm/people[/:id]` and `/crm/companies[/:id]`; legacy `/contacts` paths redirect. View state (search, filters, sort, page) is in the URL and evaluated on the server. See [ADR 0007](decisions/0007-crm-companies-and-links.md) and [the acceptance record](acceptance/crm-01-02.md).
