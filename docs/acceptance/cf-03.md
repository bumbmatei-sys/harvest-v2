# CF-03 acceptance

CF-03 exercises Harvest authentication and single-file storage in a local Workers runtime. The probe uses the same API handlers and PostgreSQL rules as the Node app. It uses synthetic users, embedded PostgreSQL and local R2. Its mailbox is a fake service binding. All five HC-02 gates remain **UNAPPROVED**. This change requires no database migration. [Infrastructure PRD](../prd/cloudflare-infrastructure-migration.md) · [CF-02 request scopes](../plans/cf-02-request-scoped-db.md)

## What the local checks cover

- The same workerd instance issues an email code to the fake mailbox, accepts it once and reads the resulting database session on a later request. Each request creates its own Better Auth instance when it needs one. On HTTPS, the session cookie is host-only with `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/` and a seven-day lifetime. Sign-out clears the cookie and invalidates the old session. Preview and simulated production use different hosts, cookie names, signing material, databases and buckets. The probe also submits a copied preview cookie directly to simulated production.
- The Worker reads bindings on each request. A missing stage, declared production origin, database name, Hyperdrive binding, bucket, mail configuration or signing secret stops the request. The production origin must match the explicit production stage. QA sign-in settings are rejected on the Workers path. The probe checks a missing production secret, an unexpected request host and a foreign POST origin. The Node environment and QA alias keep their existing behavior.
- The file API uses existing membership, ownership and guest-resource rules. The Worker signs short-lived, method-specific transfer URLs. A private URL requires the session of the user who received it. A wrong tenant or unavailable file is refused before a grant is issued. The upload stream is bounded to the file's declared length and the existing 10 MiB ceiling. The MIME allowlist, original checksum, write-once condition and confirmation byte inspection still apply. A ready private file streams back through the API as an attachment. The guest test enrolls a reader in a free resource and checks that a different session cannot use that reader's URL. The public download test starts from a synthetic post-scan file.
- The harness scans runtime logs, response bodies and response headers for generated fixture secrets. It also scans the emitted client assets. Better Auth's public library contains the name of its secret environment variable. The scan checks values and Harvest's server-only and test-only markers. Successful Worker auth responses return session credentials in the HttpOnly cookie and omit the token from JSON.
- Node's existing tests exercise mocked-mail OTP, cookie creation and sign-out, and S3 upload, download and quarantine with a loopback storage fake. A new unit test also verifies that the same S3 singleton and private presign parameters are used on the ordinary Node file routes.

## Cache rules

1. Set `Cache-Control: private, no-store` on auth, tenant and guest-resource responses, including errors and redirects, and on every file transfer. Never put session-bearing, user-specific or tenant-specific HTML, API responses or transfer URLs into the edge cache, Next cache, browser service worker or shared KV. Keep authenticated Hyperdrive query caching disabled.
2. Use `Referrer-Policy: no-referrer` on grants and file responses. Keep request query strings, session cookies, transfer URLs, OTPs, provider payloads and credentials out of log fields. Check account-level request logging and traces before enabling them for these routes.
3. A ready public file can have an anonymous route. Its short-lived redirect and file response still bypass caches. A public page or API may enter a shared cache only after review of its inputs and invalidation policy. Cache keys must account for the host, locale and any other public variation. Keep static build assets and the public offline shell on their existing cache policy.

## Repeat the local check

Use a disposable checkout with `npm ci` and no copied environment files. Install the CF-01 pins in a separate directory. Use OpenNext `1.20.18`, Wrangler `4.166.0`, Miniflare `5.20261117.0-beta`, and workerd `1.20261117.1`. Copy the OpenNext and Wrangler templates from `spikes/cf-01` into the disposable checkout as `open-next.config.ts` and `wrangler.json`. Set `assets.html_handling` to `none`, as in CF-01. Link `$CF03_TOOLING/node_modules/@opennextjs/cloudflare` into the checkout under `node_modules/@opennextjs/cloudflare` so the copied configuration can resolve it. Run `$CF03_TOOLING/node_modules/.bin/opennextjs-cloudflare build` with telemetry disabled and no provider environment. The build emits the client files under `.next/static`.

Compile the existing Linux loopback guard and run the probe from that checkout. It creates fresh databases and injects all test secrets in memory.

```sh
cc -x c -shared -fPIC spikes/cf-01/loopback.c.in -ldl -o "$CF03_TOOLING/loopback.so"
env -i PATH="$PATH" LANG=C.UTF-8 LC_ALL=C.UTF-8 \
  LD_PRELOAD="$CF03_TOOLING/loopback.so" CLOUDFLARE_CF_FETCH_ENABLED=false WRANGLER_SEND_METRICS=false \
  CF03_MINIFLARE_MODULE="$CF03_TOOLING/node_modules/miniflare/dist/src/index.js" \
  CF03_CLIENT_ASSETS="$PWD/.next/static" \
  node --import tsx tests/cf03/run-local.ts
```

For a build-time check, generate a disposable canary in memory, pass it to the build as `BETTER_AUTH_SECRET`, `FILE_GRANT_SECRET` and `RESEND_API_KEY`, and pass the same value to the probe as `CF03_BUILD_CANARY`. The harness prints only the scan result and number of assets.

## Hosted Cloudflare run · 26 Nov 2026

Founder-authorized disposable resources, all deleted after the run: a schema-only Neon branch with the 112 migrations through 0113 applied by the owner, a cache-disabled Hyperdrive config for the `harvest_app` login, a private R2 file bucket, a separate R2 bucket for the synthetic mailbox, the buffered API fixture from `prepare-remote.ts` as `HARVEST_ENV=staging` on a workers.dev origin, and the staging-only harness Worker (`tests/cf03/harness-worker.ts`). The harness serves the fixture's `MAILBOX` binding, accepts only synthetic `@example.invalid` recipients, and runs the seed steps the local run performs in Node through the same `withDb` path. Secrets were generated for the run and never printed. `tests/cf03/run-staging.ts` (skips by default and in CI) passed:

- **OTP and cookies:** sign-in through the real edge, `__Secure-harvest-staging.session_token` with Secure, HttpOnly, SameSite=Lax, Path=/, Max-Age=604800 and no Domain; no token in JSON; reused code refused; a production-named cookie refused.
- **Client IP:** Cloudflare refuses a client-supplied `cf-connecting-ip` at the edge (403, error 1000) before the Worker runs. Requests carrying forged `x-forwarded-for` and `x-real-ip` recorded Cloudflare's client IP on the session, not the forged value.
- **Closed gates and origin:** `/api/qa/otp` 404; a foreign `Origin` 403.
- **Files on real R2:** non-member 403, oversize and HTML 400, wrong user 404, wrong type 415, wrong length 400, wrong checksum 409, upload 201, repeat upload 409 (write-once), confirm `ready`, two downloads byte-identical as `application/octet-stream` attachments, other user / anonymous / tampered grant 404, private file not public.
- **Guest and uploader rules:** catalog file hidden before enrolment, guest grant usable only by the guest, a member cannot confirm another person's upload.
- **Edge cache:** every response `private, no-store` with no edge cache hit; after sign-out the old cookie is 401 and the old grant 404.
- **Hosted logs:** 64 log events from both Workers; none contained any generated secret. Cloudflare's own request logging shows `cookie: REDACTED` and `grant=REDACTED` for transfer URLs.

Not covered here: the public download redirect (it needs the post-scan state, which only the owner can seed), the full OpenNext page and middleware runtime, max-size and concurrent transfer memory, and a custom staging hostname.
