# HC-02 — Harvest Connect data foundation (tenant schema, RLS, rights hooks)

Date: 2026-11-07. Baseline: `main` at `37a3f5e` (CRM-01–08, CW-01, HC-01, HC-04 merged; last migration `0025_crm_webhooks_ai_approvals`). Migration: **`0026_hc02_connect_intake`**. Scope source: [slice plan](../prd/harvest-connect-slices.md) HC-02 row, [Connect PRD](../prd/harvest-connect-qr-to-discipleship.md) §§5, 9, 11, 15–19, [ADR 0011](../decisions/0011-harvest-connect.md), [threat model](../security/harvest-connect-threat-model.md).

HC-02 is a **data foundation only**. It adds no public route, intake API, UI, invitation, delivery, job handler or webhook. Nothing in it can collect a real guest response from the internet, associate a CRM record, or send anything.

The CRM handoff happens in HC-06 (see §4) |

| Pending guest data | **Nothing** | **New restricted pending tables**, kept separate from CRM (below) |

### Contract encoded (engineering choices, all fail-closed)

1. **Forms ownership and notice versions.**
   - Generic `forms` and `form_versions` tables, named for the Forms module so that registration forms can reuse them later. The Forms builder/product is not implemented.
   - `privacy_notice_versions` stores exactly the copy a workspace owner or admin publishes, keyed by notice key, locale and version.
     - The insert trigger computes the SHA-256 server-side; a caller-supplied hash is overwritten.
     - Rows are immutable, even to owner DML.
     - Harvest supplies **no notice text**. Test fixtures say "Synthetic … not approved copy".
   - A form version moves `draft → published → retired`. Publishing requires all of:
     - a notice version from the same workspace;
     - an explicit retention setting;
     - one or more distinct allowed purposes;
     - the publisher must be the acting user.
   - A published version is frozen. Only retirement is allowed, and a retired version is final.
   - **Consent evidence references** the exact `form_version_id` and that version's `notice_version_id`, through composite FKs. The guard rejects any mismatch.
2. **Restricted pending guest data.**
   - `campaign_response_links` (QR/short-URL source) belongs to one campaign. Its global unique 32-hex `public_code` is not personal data.
   - `campaign_responses` must agree with its link's campaign **and** form version. This is enforced by a 4-column composite FK and also by the guard.
   - A response is accepted only when:
     - the link is published;
     - the form version is published;
     - the campaign is not archived.
   - `submitted_at` and `expires_at` are set by the server, and every response starts `pending` with no contact.
   - `(tenant_id, campaign_id, public_submission_id)` is unique, so a retried submission yields one response.
   - `campaign_response_contact_methods` holds addresses awaiting verification. They always start unverified.
3. **Separate opt-ins.**
   - `campaign_response_consents` stores one append-only row per purpose: at most one grant and at most one withdrawal.
   - A grant must:
     - come from the subject (staff can never record a grant);
     - be for a purpose that this form version offered;
     - name a channel only when a matching contact method exists.
   - A response never creates a contact, CRM consent, membership, outbox event or job. A test checks these counts before and after a response.
4. **Withdrawal, erasure and handoff.** See §3 and §4.
5. **Retention.**
   - `form_versions.pending_retention_days` has **no default**, and a version cannot publish without it. The value is the workspace's legally reviewed setting. The `1..36500` check only prevents date overflow; it is not a policy.
   - `expires_at = submitted_at + retention`, computed by the guard.
   - `purge_expired_connect_responses` erases expired pending responses.

## 2. Access matrix (`harvest_app`)

| Table | Grant | Who (RLS) |
| --- | --- | --- |
| `privacy_notice_versions` | SELECT, INSERT | Read: any member. Write: owner/admin, `created_by` = actor. Immutable |
| `forms` | SELECT, INSERT | Read: any member. Write: owner/admin |
| `form_versions` | SELECT, INSERT, UPDATE | Read: any member. Write: owner/admin. The guard enforces the lifecycle |
| `campaign_response_links` | SELECT, INSERT | Read: any member. Insert: owner/admin/member, **draft only**. Publish/disable/rotate is HC-03 and has no grant |
| `campaign_responses` | **Column SELECT only**: ids, status, timestamps | Owner/admin only. `preferred_name`, `public_submission_id`, `locale` and `contact_id` are not selectable by any role. No INSERT/UPDATE/DELETE |
| `campaign_response_contact_methods` | **None** | No application access |
| `campaign_response_consents` | SELECT | Owner/admin only. No INSERT: grants arrive through HC-05's intake definer, withdrawals through the definer below |

- No policy names `PUBLIC`.
- The migration role gets the same `erasure_owner_tenant` policy on the three pending tables that it has on the CRM tables. It also gets a read-only, tenant-scoped `connect_definer_read` policy on `form_versions`, used by the withdrawal provenance check (review B2).
- Permission `connect:privacy` is owner/admin, and is used by `src/server/connect-responses.ts`.

## 3. Rights hooks

| Function | Caller | Effect |
| --- | --- | --- |
| `withdraw_connect_response_purpose(tenant, response, purpose)` | Owner/admin in tenant context | Appends a staff withdrawal for one purpose. Other purposes stay in force. Returns `withdrawn` / `already_withdrawn` / `not_granted` / `not_pending` / `not_found`. Audit row `connect.response.withdraw` with the purpose |
| `connect_response_purpose_active(tenant, response, purpose)` | Owner/admin: authenticated actor with live membership in the tenant context (review B1) | Boolean recheck that every future sender or assigner must call immediately before acting. False after withdrawal, erasure or expiry. A future worker needs its own separately constrained capability |
| `erase_connect_response(tenant, response)` | Owner/admin | Erases the response (steps below), then writes audit `connect.response.erase` with no target |
| `purge_expired_connect_responses(tenant)` | Owner/admin | Erases expired pending rows (`SKIP LOCKED`). One aggregate `connect.response.purge` count |
| `erase_contact` (replaced) | Unchanged | Also scrubs every Connect response associated with the person, before the person is re-keyed |

`erase_connect_response` removes, in order:
1. the contact methods;
2. the evidence detail: channel and staff id removed, times truncated to the day, row marked redacted, and **evidence ids re-keyed** (review B3);
3. `responseId` references in the outbox and jobs;
4. the name, locale, submission key and contact link;
5. links from `connect.response.*` audit rows to the response;

and finally re-keys the response into a day-level tombstone. The tombstone keeps only campaign, link, form version and day. No app-readable key observed before erasure (response id, submission key, evidence ids) or exact evidence time survives it.

- The scrub helper `connect_scrub_response` has invoker rights and no `harvest_app` EXECUTE.
- Guards admit row changes only from the owners of the erasure definers.
- The audit ledger stays append-only. Its new branch allows only nulling a `connect.response.*` target that points at an erased tombstone.

## 4. Verified-association handoff (for HC-06 / HC-07)

- `campaign_responses.contact_id` and `associated_at` are **reserved**.
- Under HC-02, no role can set `contact_id`: the guard rejects it even for owner DML. The composite FK also rejects another workspace's contact.
- HC-06 must add a definer that:
  1. requires HC-07's verified one-use claim;
  2. reuses CRM tenant identifier dedupe;
  3. records CRM `contact_consents` from the pending evidence. A CRM notice-version reference to `privacy_notice_versions` (instead of the `notice-v1` text allowlist) is HC-06's ledger change;
  4. deletes the pending contact methods once they become CRM identifiers;
  5. **moves** a merge source's responses in `merge_contacts` before that function calls `erase_contact`. Today a merge would erase those responses: privacy-safe, but they would be lost. The case cannot occur yet, because nothing can set `contact_id`.
- After association, `withdraw_connect_response_purpose` returns `not_pending`, because the CRM ledger owns the person's choices from then on.

## 5. Decisions for Matei (encoded as the most restrictive default; confirm before HC-05 collects real data)

1. **Purpose mapping.** The form-offerable purposes are the existing ledger names:
   - `account_communications` — sign-in/invitation;
   - `outreach_follow_up` — pastoral contact;
   - `newsletter`.

   Church referral (recipient-scoped, HC-18), generic `marketing` and any religious-response classification are deliberately **not** offerable. *Recommendation: approve this mapping. Legal basis per purpose remains a legal-review gate.*
2. **Who may see pending metadata and act on rights requests.** Owner/admin only. No campaign role sees names or contact methods. *Recommendation: keep this until HC-13 defines assignment-scoped counselor access.*
3. **Tombstone after erasure.** This follows the CRM precedent: day-level campaign/link/form-version row and redacted evidence (purpose, status, day). *Recommendation: approve, or choose full deletion instead.* This is a privacy-review item.
4. **Retention values.** Each form version must set its own retention; none is chosen. A platform maximum and the legally approved durations are **pending legal review**.
5. **Contact-method protection.** Values are plaintext under zero application grants, plus database encryption at rest. Application-layer encryption and key management are a **security-review decision** before HC-05/HC-07 store real addresses.

  - another workspace's identical guest is untouched;
  - audit stays append-only outside controlled erasure.

## 7. Limitations and deferred work

- **HC-03:**
  - publishing, disabling, rotating and expiring links has no grant (tests seed `published`);
  - whether publishing requires an `active` campaign;
  - the DB-backed public resolver for HC-04's static preview.
- **HC-05:**
  - the constrained public intake definer: tenant derived from the published `public_code`, abuse controls, payload validation, normalization, and HTTP idempotency semantics;
  - migration-role read policies on `campaign_response_links` and `campaigns`, if its definer must read them under FORCE RLS (`form_versions` already has one since review B2);
  - no free-text or sensitive fields exist, and none may be added without approved safeguards.
- **HC-06 / HC-07:** see §4. Contact methods cannot be read or verified yet.
- **HC-13 / HC-14 / HC-15:**
  - assignment-scoped access;
  - guest self-service withdrawal/DSAR through a verified claim;
  - cancelling queued work on withdrawal. HC-02 provides only the recheck function, and there are no Connect jobs to cancel yet;
  - provider/recipient propagation;
  - aggregate metrics over tombstones.
- **Retention sweep scheduling:** `purge_expired_connect_responses` needs a system actor or job owner. Today it requires an owner or admin.
- **Events:** no `connect.*` outbox kinds are emitted. Producers must keep `responseId` top-level so the scrub can find it, and must not put a response id in idempotency keys or other nested fields.
- **Not run:** Neon CI verification (`npm run test:rls:neon` needs credentials), Playwright, and Lighthouse. This slice has no UI or route changes.
- **Not started:** HC-03, HC-05+ and CW-02+. Nothing merged, deployed or sent.
- **Pending gates** (ADR 0011 / threat model): legal/privacy, security and safeguarding reviews, and PRD §18 founder decisions. No signoff is implied.
