# Newsletter Analytics screen

Public > Newsletter > Analytics (`/workspaces/[tenantId]/newsletter/analytics`, nav id `newsletterAnalytics`, feature `newsletter`, permission `newsletter:analytics`, live only outside production like the other newsletter routes). It is the first entry of the Newsletter group (order: Analytics, Campaigns, Audience, Sign-up forms). Sending stays hard-off; nothing here sends, schedules or calls a provider. All five HC-02 gates remain UNAPPROVED.

## What the server can report (inspected)

The merged newsletter server (#165) keeps one delivery record per selected recipient for 90 days and, after that, anonymous per-day counts. Queryable per campaign and per UTC day: recipients selected, skipped (by reason), queued, attempted, failed, unconfirmed, needing review, accepted by the provider ("sent"), delivered, bounced, complained, unsubscribed. **Opens are not collected** (no tracking pixel). **Link clicks** are counted only when the ministry owner turns counting on (migration 0126, [click-tracking acceptance](newsletter-click-tracking.md)): totals per campaign, UTC day and link, groups under 5 withheld, labelled "may include link scanners". The footer says which applies. See "Server gaps".

## Done

- Overview: period tabs (7, 30, 90 days, UTC, through `?period=`), seven tiles (campaigns, sent, delivered, bounced, complaints, unsubscribed, link clicks; rates are shares of sent), a daily chart (sent, delivered, bounced, unsubscribed), a sortable campaigns table (sort by name or any figure) whose rows open that campaign's analytics, an "Audience growth" card (daily subscribed, unsubscribed, bounced or suppressed, with net change over the period; see "Audience growth and outcome days") and an "Audience now" card (the same three counts) from the Audience status data, which is derived from the consent ledger.
- Campaign analytics (`/newsletter/analytics/[campaignId]`, reached from a table row or the Analytics item in the Campaigns list row menu; the sidebar stays on Analytics): tiles with rates, the series since send (at least a week, from the first day with records, up to 90 days; each outcome charted on the day it was recorded, clicks on the day of the click), and the delivery status breakdown. Drafts and unsent campaigns show "Not sent yet". Top links (5 or more clicks) appear once counting is on.
- Empty state: "No sends yet" because sending is off; tiles read zero.
- Privacy: aggregate only, no recipient is ever listed or returned. Groups under 5 are withheld by the server's existing rule and shown as "Fewer than 5" (tiles, table cells, chart gaps, audience counts of 1 to 4). A period total is withheld when any day in it is a small group. Do not contact wins in the derived audience status and in send-time eligibility already. UTC throughout. Windows end at 90 days; nothing older is implied.
- Permissions: owners and admins only. The server capability `newsletter:analytics` (RLS on deliveries, SECURITY DEFINER functions) is owner and admin, so members and viewers see the no-access note and no sidebar link; other ministries get 404. (The brief allowed member read; the existing server model does not, and changing it needs a migration.)
- Navigation: planned entry made live and moved to the top of the group. CRM Campaigns (`/campaigns`) is not matched on any `/newsletter/*` route (unit test and e2e).

## Audience growth and outcome days (acceptance, 27 Nov 2026)

**Snapshot.** `newsletter_audience_snapshots` (migration 0127, chained after 0126_newsletter_click_tracking): `tenant_id`, `day`, `subscribed`, `unsubscribed`, `suppressed`, `taken_at`. Counts only, no person, contact or subscriber id. FORCE RLS, no table privileges for `harvest_app` or `harvest_worker` (same as the other newsletter evidence tables). `public.newsletter_snapshot_audience(limit)` (SECURITY DEFINER, worker login only, pinned `search_path`, schema-qualified, restores every `app.*` flag it sets) counts each ministry with `newsletter_audience_counts`, the SQL twin of `audienceStatusSql` (a test asserts the two agree), and inserts one row per ministry per UTC day with `ON CONFLICT DO NOTHING`: a second run, or two at once, adds nothing. A worker-only `workspaces` read policy (`newsletter_growth_ministries`) lets the function list ministries. It is keyed on a random token, not on a flag alone: the function inserts the token into `newsletter_growth_scans` (FORCE RLS, no privileges for any login) for the current transaction, points `app.nl_growth_scan` at it and deletes it before returning, so a worker session that sets the flag by hand and calls another definer that reads `workspaces` sees nothing (tested). Command: `npm run newsletter:audience:test` (`scripts/run-newsletter-worker.ts audience-snapshot`), behind the daily maintenance flag `HARVEST_NEWSLETTER_RETENTION_ENABLED` and the usual non-production gate, using `WORKER_DATABASE_URL`. No backfill: the table starts empty.

**Reading.** `public.newsletter_audience_growth(tenant, from, until)` checks the ministry and `newsletter:analytics` through `public.access_role(...)` (owners and admins), allows at most 90 days, and returns NULL for any count of 1 to 4. The overview turns it into one point per day: a day without a snapshot is "No data yet" (a gap and a table cell), never zero; a withheld count is "Fewer than 5". Net change is the last snapshot minus the first in the period, withheld when either end is withheld, and "No data yet" with fewer than two snapshots. The card notes "No data yet before {date}" when snapshots start inside the period. Differencing: consecutive visible counts can differ by 1 to 4; that difference is of two visible counts (like the "Audience now" figures), so it is not separately withheld.

**Outcome days.** `public.newsletter_outcome_days(tenant, campaign, from, until)` (same checks) returns per-day counts of `accepted_at`, `delivered_at`, `bounced_at`, `complained_at` and `unsubscribed_at` from live delivery records, plus `archived` (the campaign has rolled-up counts) and `withheld`. **Cohort rule:** the outcome series is withheld as a whole when any UTC selection day of the campaign (live records and rolled-up counts, over the campaign's whole history, not only the window) has fewer than 5 recipients selected, or when the campaign's selection-day totals are withheld; then no days are returned and every day reads "Fewer than 5". Otherwise the per-day outcome counts are shown as they are, like outcome counts inside a visible selection-day cohort: an outcome count of 1 to 4 on one day is not withheld on its own, because the cohort it belongs to is 5 or more. The campaign page charts these; totals, tiles and the status breakdown are unchanged.

**UI.** `ReportTrendCard` gained an optional `noDataLabel` (points marked `noData`) and an optional slot above the chart (the net change figures); no new kit item. Light and dark, 360 and 1280, full width, 44px targets unchanged.

**Evidence.** Integration (restricted migration owner): `tests/integration/newsletter-audience-growth.test.ts`: flag and worker login required; idempotent per ministry per day, concurrent runs, parity with the Audience status counts; counts-only columns; FORCE RLS and no app/worker table access; two ministries kept apart; small-group hiding in the series and net change; no data before the first snapshot; owners and admins only (members, viewers and other ministries refused, including a direct call); flag restored; outcome-day bucketing; rolled-up campaigns flagged; small campaigns withheld. E2E: `tests/e2e/newsletter-audience-growth.spec.ts` (growth chart, net change, "No data yet", axe and no horizontal scroll at 1280 and 360 in light and dark). Screenshots: `docs/screenshots/newsletter-analytics/growth-*.png`; the existing analytics screenshots were re-taken with the growth card. No backfill, so no before-migration hook was needed.

## Small-group differencing (known, low risk)

A campaign row is withheld when any of its days is a group under 5, and the server withholds the period total and that day whenever any campaign-day is small. So a withheld row always comes with a withheld total, and an admin cannot subtract visible rows from a total to recover it. Rows beyond the 50 shown are only in the total, never recoverable one by one. The existing CRM Reports complementary-suppression helper is therefore not needed here; if the server rule ever changes so the total can be visible beside a withheld row, revisit.

## Missing keys

If the suppression keys are not configured the pages show a plain "Analytics unavailable" alert instead of an error page.
