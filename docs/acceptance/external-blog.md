# External blog publishing server

Working migration `0145_external_blog`. The server reuses the social connections, credential envelope, provider port, fake, and vendor adapter. The API, production transport, and remote image endpoint remain hard-off through the existing integration gate. The local worker runs only when explicitly invoked in a non-production environment against a loopback database with a worker login and the in-memory fake. No schedule or webhook was installed. All HC-02 activation gates remain **UNAPPROVED**.

## Publish step API

- `GET /api/workspaces/{tenantId}/blog/destinations` lists accounts and the cached blogs with their health, authorization and platform capabilities. Owners and admins can refresh a connection with `POST .../destinations/{connectionId}`. The app role has SELECT only on the destination catalog. Refresh writes go through the `blog_external_refresh` definer, which checks owner/admin membership and the connection version. The disconnect trigger and worker use their own scoped definers. Website managers can read the destination catalog and publish articles with the native blog capability.
- `POST .../destinations` accepts `{action:"start",platform,shop?}` or `{action:"finish",attempt}`. Start returns an opaque, actor-bound attempt and a sign-in URL. The editor can retain the attempt across navigation and submit it on return. Only Shopify requires a `myshopify.com` store domain. Harvest verifies the account under the isolated profile it created, then seals the server-owned API credential in the social connection. The connect API does not take platform secrets or trust account IDs from the browser. The default registry has no live sign-in credential wired.
- The existing article save accepts `harvestPage`, defaulting to true. With it off, the editorial schedule still works and the article stays absent from public index, article, latest, image and RSS reads. This revision has no sitemap route.
- `GET .../posts/{postId}/destinations` returns conversion warnings, canonical availability, delivery state, and whether a Harvest schedule change needs an explicit update. `POST` accepts `{version,destinationId,operation,timing?,tags?}`. The operations are `push`, `update`, and `check`. Choose `{mode:"draft"}`, `{mode:"same_time"}`, or `{mode:"own_time",at}` for push or update. Saving or rescheduling in Harvest does not enqueue an external update. Unpublishing a destination is an explicit update with draft timing.
- `GET .../blog/planner?from=…&to=…&includeDestinations=1` returns `{articles,destinations}` with destination entries linked by `postId`. Existing calls still receive the native articles array.

## Screens

Built only from existing Harvest parts (EditorShell's Publish step, `FormSection`, `StatusBadge`, `NativeSelect`, `Field`, `Switch`, `EmptyState`, `PlatformLogo`); no new kit item.

- **Publish step, "Also publish to"** (`src/components/blog/external-blog-section.tsx`): one row per connected blog with its platform type, a status chip (Not sent, Queued, Scheduled, Published, Draft, Failed, Changed on blog, plus "Reconnect needed" when the blog is unavailable), a Timing select (Draft, Same time, Own time with a date and time), the server's list of elements that are not carried over, and "Open copy" once the blog returns a link. Same time needs a Harvest time; a blog without its own scheduler offers only Draft (and Same time once the article is published). Sending saves pending editor changes first. "Update on <blog>" appears only when the article changed since the last push, the Harvest time moved, or the blog copy changed; "Check status" appears after a disputed create. Canonical is not shown: every destination reports it unsupported today.
- **Harvest page switch** on the Publish step, saved with the article. Off hides "Open article"; the schedule and copies keep working.
- **Empty state**: "No blogs connected" with "Connect a blog" linking to the account connections screen.
- **Planner**: each non-draft copy is its own chip at its blog time (platform logo, accessible label "<Platform> copy, <status>, <title>") in week, month and the overlap list, and phone agenda and month day lists now show articles and copies as rows; each opens the article. Draft copies have no time and are not shown.
- The destination routes use the same non-production gate as the Social Publish routes (`socialRouteDeps`: the in-memory fake outside production, the hard-off defaults in production). The remote image route stays on `SOCIAL_INTEGRATION_ENABLED`, which is `false`.
- e2e: `tests/e2e/blog-external.spec.ts` (seeded synthetic connections and blogs; worker outcomes set in the local database because no worker runs) covers the empty state, the three modes through the real queue route, every status, the update button and its explicit update job, Harvest page off, planner chips and the phone agenda, with axe at 1280 and 360 in light and dark, 44px targets and no horizontal overflow.

A future date uses `publishDate`. Drafts send `isPublished:false` without a date. Harvest reports `unsupported` for canonical URLs when the Harvest page is on and `not_requested` when it is off. The cover limit documented by the provider is 10 MB. A previously set cover stays in place if an update omits it. The adapter records a remote HTTPS link when returned. WordPress and Wix document a public URL after publication. Shopify and Webflow do not guarantee it in the provider schema. [Create](https://docs.zernio.com/blogs/create-blog-article) · [Update](https://docs.zernio.com/blogs/update-blog-article) · [Read](https://docs.zernio.com/blogs/get-blog-article)

Provider-visible image URLs carry random IDs and stream only the associated ready image. They contain no private object keys or storage redirects. A link works only while an article in the same ministry still uses the file as its cover or a body image and has a delivery that either holds a remote article or has a pending job. Removing the picture from the article, deleting the article, or removing the source file returns 404. Destinations that hotlink instead of importing lose that picture at that point. The same private media endpoint is used for cover and body images.

## Jobs, retention and verification

The queue freezes the Harvest payload and job UUID at the selected article version. A restricted worker claim commits before each provider request and completion checks the current lease. Creates reconcile by a deterministic article handle before another attempt and reuse the original key. WordPress and Webflow document lookup by handle, while Wix and Shopify use a bounded listing. A disputed write that cannot be resolved after four attempts or after its deduplication window requires an explicit status check. Harvest uses a conservative cutoff 23 hours after queueing for an attempted create. The documented key lifetime is 24 hours. Harvest keeps the original key for reconciliation. [Idempotency guide](https://docs.zernio.com/guides/idempotency) Disconnect cancels pending work. A request already delivered to a platform may complete there.

The delivery state records the hash of the remote article content returned by the provider. An explicit status check compares a fresh full remote article. Remote bodies never enter the database. Job completion removes the queued Harvest payload, and audit rows record only IDs, versions, and fixed outcomes. Deleting a Harvest article removes its local delivery metadata and never calls the destination's delete endpoint.

Local evidence uses a fake provider, injected wire fixtures and synthetic `@example.invalid` data. Hosted Neon, real sign-in, adapter parity, the hosted media path and real destination rendering remain unverified. Self-hosted WordPress documents an application-password flow, so Harvest only offers the documented WordPress.com sign-in. The founder can decide whether the UI should offer Webflow draft as the fallback for scheduled publication.
