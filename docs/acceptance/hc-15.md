# HC-15 campaign Connect metrics

Server/API only; built toward the engineering direction, **UNAPPROVED, not activated**. All five HC-02 gates remain UNAPPROVED. Production collection/delivery remain hard-disabled; production migrations 0031+ unapplied. No UI, message key or navigation entry is added; those belong to the UI workstream.

Migration **0054** depends on the personal-provider draft's **0053** solely to preserve the Drizzle journal/snapshot chain. This PR is stacked on that draft; it must follow 0053 and must not be independently applied to a 0052 database. No merged migration is modified or renumbered.

`getCampaignConnectMetrics` and `GET /api/workspaces/[tenantId]/campaigns/[campaignId]/connect-metrics` require owner/admin membership. The SECURITY DEFINER also checks live membership with a share lock and tenant context, obeys FORCE RLS as a restricted owner, pins `search_path = pg_catalog, pg_temp`, and is revoked from PUBLIC. Existing application read policies on cases and responses are unchanged. Only counter storage and an owner-only response aggregate policy are new. No public endpoint returns a count; the authenticated route is private/no-store.

Counts include campaign QR/short-link resolutions, pending/associated/erased responses, currently associated verified claims (same cohort as associated, not a historical identifier-retaining claim ledger), and every follow-up case state. Erased claims are not retained as identifiable verified claims. There is no total, percentage, per-person field, drilldown, date/source filter or time series. Results have a fixed allowlist of numeric-or-null keys only.

## Suppression

Every cell passes `connect_suppress_small`; the TypeScript defense also uses `suppressSmall`. Counts 1–4 return null. If any cell is small, or any two subset sums of the released counts have a difference of 1–4, the entire related metric vector is suppressed, including zeros and larger complementary cells. This conservative rule trades detail for preventing subtraction from the released vector, including sums of multiple breakdown cells. Counts 0 and 5 are visible when the rest of the vector is safe. SQL/TS parity covers mixed cells. Repeated live observations and external knowledge are not a differential-privacy guarantee; privacy/legal review of release policy remains required before real-data activation.

## Scan storage and collection

`campaign_scan_days` stores only ministry, campaign, UTC day and a nonnegative integer count. Composite tenant/campaign FK and FORCE RLS; no application table grants. No IP, user agent, visitor id, per-scan row, exact scan timestamp, contact link or request headers. A definer resolves the campaign from a currently published/unexpired code, checks campaign lifecycle, and atomically increments the day counter. It rejects disabled/unknown codes and requires synthetic intake mode.

The public server landing boundary calls scan capture only when the existing local synthetic gate is satisfied; production unconditionally refuses that mode. Static preview does not count; React request caching avoids page/metadata double-counting. These are resolutions, not unique people; reloads can count again. There is no unique-visitor claim. No production collection is enabled. Day counters have no new retention/purge schedule; policy and operations remain gates before activation.
