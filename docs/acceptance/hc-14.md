## Behavior

- A recorded CRM `outreach_follow_up` withdrawal on any channel atomically moves every affected non-terminal case to `withdrawn`, clears its assignee, increments its version through the existing guard and writes one `followup.case.withdraw` audit. The transition table is unchanged: all six non-terminal states already allow withdrawal. Closed/withdrawn cases stay terminal. Repeated withdrawals produce no extra case mutation/audit; later grants never reopen a case.
- Response withdrawals, including verified subject-rights requests, already project into the CRM ledger. That existing projection now invokes the same trigger. No new public rights endpoint or staff access is introduced. The existing pending-response staff operation remains limited to pending responses.
- Outstanding withdrawal follows 0050: any channel blocks until a grant on that same channel is later on both clocks. Other purposes and missing grants alone do not cause an automatic withdrawal.
- Merge rechecks the kept contact's ledger after moving the response/case. A deferred constraint trigger checks moved consent rows against the final ledger at transaction end, including target cases when the source has no response. This avoids acting on an intermediate historical withdrawal already superseded by a grant. Erasure records the legal terminal transition before deleting a case with the scrubbed response; no new identifying tombstone is retained.
- An owner-only temporary scan reconciles pre-existing open cases with outstanding withdrawals during upgrade, including a populated 0050 database. The scan policy is removed before commit. The journal timestamp exceeds 0051 and the generated snapshot chains from 0051. No merged migration is edited.
- The helper locks the live contact before locking its cases, matching opening/merge ordering. A racing case operation may finish before withdrawal commits; withdrawal must then close the case before its own commit. A lock conflict may require retrying a request; no sender is added here.

## System actor decision (Task 5)

`audit_logs.actor_id` is nullable, with a CHECK permitting NULL only for `followup.case.withdraw` and `followup.case.revoke`. NULL means automation with no user actor, even when a staff request triggered the side effect. The initiating consent/membership operation retains its own human provenance. Revocation no longer falsely attributes automation to the removed member or the current staff user.

A reserved user row would introduce an artificial identity in the authentication tables and require protecting it from login, membership and mutation. NULL represents the fact directly without creating that identity. Existing non-null actors and their foreign key remain intact. The application audit INSERT policy is unchanged and still requires equality with the session actor: application-role inserts cannot impersonate NULL system actions. Definer helpers are revoked from PUBLIC and have no application EXECUTE grants; each SECURITY DEFINER uses `SET search_path = pg_catalog, pg_temp`. FORCE RLS remains in place. Server activity/deal readers filter null actor ids before member lookup and carry the nullable type; no component changes are needed.

## Staff procedure and remaining gaps

[Staff rights-request runbook](../runbooks/connect-rights-requests.md) is documentation only, UNAPPROVED and not operationally verified. It describes verification, least disclosure, scope, permitted actions, completion checks and escalation. HC-14 does not build a staff DSAR export workflow.

Denial logging is **not done**. Existing audit writes share the transaction that raises a permission error, so they roll back with a denial. There is no durable, independent denial-audit pattern to reuse without extending the logging design. No personal data or database error strings are added to logs. Audit/request-register retention, legal deadlines, identity-verification policy, designated privacy owner and alert/delivery channels remain decisions before operational use. CRM-wide contact visibility remains a separate UNAPPROVED prerequisite.
