Design: [C11 chat design](../superpowers/specs/2026-11-17-communities-c11-chat-design.md), sections 4–10, 12–14, 17–19. Migration: **0057_community_chat**, following 0056; journal time `1795400000005`. Initial main: `829a9e1`; reconciled with `901b4a1` (#120) by merging main. No UI, DM tables, scheduler, merge, deployment or production activation.

## Delivered

- Channel creation takes the state-row lock last before checking capacity, including when every channel row has been deleted; 31 concurrent admins yield exactly 30 creates and one limit outcome. Read-only channels reject member reactions.
- Channels with General initialization for existing/new communities, access modes, host posting, slow mode, ordered management, invite membership and archive. Tier/tag modes remain schema values refused by the server. Settings are audited.
- Plain-text messages, validated mention ids, flattened one-level threads, five pins, twelve reactions, author edits and soft deletion/recovery. Hosts retain deleted bodies; member polling returns body-free tombstones. An author cannot convert a host removal into an author deletion to bypass restoration permissions.
- FORCE RLS on every new table, scoped restricted-owner policies, composite ownership foreign keys, SELECT-only application grants and narrow SECURITY DEFINER entrypoints with PUBLIC execution revoked and fixed `search_path`.
- Channel revisions serialize writers in commit order. Poll cursors are the maximum revision actually returned, including capped pages; history uses immutable sequence positions. Bigint positions/revisions cross JSON as decimal strings.
- Read-state clamping and per-channel mute; bounded unread/mention counts (100 means “99+”). Membership/grant/invite changes bump personal state. Channel writers lock author advisory key (send), channels in ascending id, affected memberships in ascending user id, then the separate community state row last. Message writes never update the wide community row.
- Ministry hosts without a community membership use a detector derived only from their own read rows; ordinary members use their stored `chat_state_rev`. Rail ETags hash reader identity, sorted readable `(channel_id,last_rev)` pairs and that reader's personal revision. Neither the global counter nor unreadable channel activity enters the detector. Unchanged rail polling skips unread aggregates; channel polling has a counter/304 path. A capped change page is not incorrectly answered 304 while later revisions remain.
- Message reporting, grouped queue descriptions, a Chat held-content source, rank-aware removal/pins and owner/admin restoration, held decisions, moderation actions and channel-report decisions. Open-report targets are protected from purge; deciding a deleted-message report restarts its 30-day recovery period.
- Mention/thread notifications extend and call the canonical `community_notify_as` C15 helper and use existing C15 storage, group by channel, respect community/channel mute and current access, and contain no message body. Chat kinds are digest-only; DM digest notices stay off in this slice. Notification constraints retain every existing kind/target and admit the C11 kinds/targets. Delivery remains hard-disabled.
- Worker-only channel purge, counts-only run log, failure recording and health. The grant block refuses a privileged/inheriting worker role and is replayable after provisioning. Purging a root preserves its still-live replies by clearing only their parent id. The composite FK's column-specific `SET NULL (parent_id)` is handwritten SQL; Drizzle's snapshot records `set null` but cannot express its column list.
- API routes under `/api/communities/[slug]/chat/`: state; channels/list/create/save/delete/reorder/invite membership; messages/list/send/edit/delete/restore/react/moderate; read/mute; settings; reports/decisions; Chat held source. Existing C12 routes also accept channel-message targets.

### Serialization exit measurement

Synthetic local embedded Postgres, 12 concurrent authenticated writers, one message each, separate application connections. Final focused sample: one channel **237 ms wall, 122 ms p50, 216 ms p95**; three channels **53 ms wall, 29 ms p50, 52 ms p95**. Both batches together incremented the single community state row exactly 24 times. Polling the shared channel afterwards recovered all 16 messages in capped pages. The test writes its latest counts-only sample to `/tmp/harvest-c11a-serialization.json`; final rerun numbers are recorded in the PR.

This measures the required single-community write serialization and the extra same-channel serialization. It includes connection/query overhead and is not a throughput guarantee, production capacity estimate or Neon benchmark. The community state row remains a serialization point even across channels; reader-scoped pair hashing permits removing that bookkeeping counter in a later measured change if needed.
