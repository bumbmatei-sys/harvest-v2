# Newsletter Sign-up forms

Public > Newsletter > Sign-up forms (`/workspaces/[tenantId]/newsletter/forms`, nav id `signupForms`, between Audience and the end of the group, feature `newsletter`, owners and admins, live only outside production like the other newsletter routes). **No second form engine**: a sign-up form is a CRM form (same `forms` and `form_versions` rows, same builder, same drafts, publication, address and hosted forms server) whose definition carries a `newsletter` block. Sending stays hard-off. The confirmation message goes to an in-memory fake sink in synthetic test mode and nowhere else. All five HC-02 activation decisions remain UNAPPROVED, and the hosted pages stay hard-off in production (`CRM_FORMS_PRODUCTION_ENABLED = false`, the `harvest_test` database-name gate in every database function).

## What works

- **List** (owners and admins): name, lists, status (Draft, Published, Unpublished), sign-ups, last sign-up, row menu (Edit, Preview, Copy link, Duplicate, Archive), search, empty state and "New sign-up form". New form opens a dialog to pick one or more existing NL-01 lists, then the shared builder.
- **Builder** (the shared `FormEditor`, `variant` by the presence of the newsletter data): the same top bar, autosave, undo, publish and unpublish. Build shows the fixed questions (email required, optional first and last name) with only their wording editable and the consent pinned, no Add question menu. Settings replace Save to, owner, labels and hidden fields with **Lists**, **Questions** (first and last name on or off), the read-only **Consent wording** (its version id, the statement and the fixed line), then the shared Submission (button, redirect address, spam check), Layout and Colors. The End page is the confirmation message. Two extra tabs: **Share** and **Sign-ups**.
- **Consent**: one required checkbox, never pre-ticked. Its label is the newsletter statement from an immutable wording catalogue (`newsletter-consent-v1`: "I agree to receive the [ministry] newsletter by email. I can unsubscribe at any time."), with Harvest's fixed line beside it ("Your details go to [ministry]. You can ask them to delete them."). Both texts are stamped by the server from the wording version and the ministry's name on every save, and again at publish, so a client cannot change them. A new wording is a new id; old ids stay.
- **Frozen into the publication**: the lists, the wording id and both texts live in the definition, which a publication freezes, so what a visitor saw never changes with a later rename or edit. (This closes the reviewer follow-up "freeze the fixed form consent line" **for sign-up forms**; plain CRM forms still render the standard line from the catalogue.) The consent block's text becomes the publication's notice version as for every hosted form.
- **Double opt-in**, reusing the NL-02 grant rules: the public form posts to the existing hosted `POST /f/:slug/submit` (same proof, origin, honeypot, spam time and the **same rate limits**: 5 per visitor per form and 20 per visitor across forms per minute, 300 per ministry, proof issue 30 per minute). For a sign-up form the server records a pending sign-up (digests, the optional names, the lists from the **published snapshot**, never from the request) and sends one confirmation message to the fake sink. No person, consent or subscription exists yet. The link (`/newsletter/confirm?email=&token=`) opens a page whose button posts to the existing `POST /api/newsletter/confirm`; only then is the person created or reused and the newsletter permission granted, once per list. Withdrawals newer than the request, other-channel withdrawals, hard suppression, bounces and a later unsubscribe all win (the sign-up ends **blocked**); an unpublished, archived or expired form grants nothing; a link works once. A refused, replayed or rate-limited submission looks exactly like a successful one. The address is never stored; a per-address cap of 3 an hour per form applies on top.
- **Share** (published forms): public link `/subscribe/<slug>` with copy button, embed snippet (iframe to `?embed=1`), QR code (the existing Connect renderer, SVG and PNG download, encoding only the address). **Sign-ups**: counts only (total, waiting for confirmation, confirmed, not confirmed) with the last sign-up time and a refresh; people appear in Audience through the CRM once they confirm, never here.
- **Public pages** (synthetic mode only): `/subscribe/<slug>` renders the published form with the shared `PublicForm` (frozen texts, confirmation message, optional redirect); `/newsletter/confirm` is the link target. Both are noindex, `Referrer-Policy: no-referrer`, no-store. An unknown, unpublished, archived or non-served form shows one neutral "not available".
- **Archive** removes the form from the list, unpublishes it and keeps what people already confirmed.
- CRM Forms list, People source filters and the CRM editor ignore sign-up forms (the CRM editor redirects to the newsletter screen).

## Server

- Migration `0088_newsletter_signup_forms` (0087 is #218 Sender setup): table `newsletter_form_signups` (FORCE RLS; owners and admins read ids, state, times and list ids only; no grant on the digests, names or contact id; **no foreign key to contacts**), `nl02_grant_list` (the grant step extracted verbatim from `nl02_accept_signup`, which now calls it, so NL-02 and hosted sign-ups cannot drift), `newsletter_form_signup_start`, `newsletter_form_signup_confirm`, `newsletter_form_archive` (SECURITY DEFINER, fixed `search_path`, `REVOKE FROM PUBLIC`, database-name gate) and a before-erase trigger that drops a person's pending rows.
- `src/server/newsletter-forms.ts` (list, create from the preset, counts, archive), `src/lib/newsletter-signup.ts` (ids, wording catalogue, stamping, preset), `newsletter-confirmation.ts` (fake sink, test read at `GET /api/newsletter/confirmation-sink?to=` in synthetic mode only), the `submitNewsletterSignup` branch of `crm-form-submission.ts`, and `confirmNewsletterSignup` now also runs the hosted confirmation. No new capability: `newsletter:manage` (owners and admins) and the existing `crm:forms_manage` (same roles) for the shared builder routes.

## Deferred and gaps

- **No real delivery**: there is no sender, so the confirmation message exists only in the fake sink. A real confirmation email needs the reviewed sending slice and a reviewed notice. The public pages are hard-off in production.
- Synthetic data only: the hosted path accepts `@example.test` addresses, like every hosted form.
- Plain CRM forms still render the standard fixed line from the catalogue rather than a frozen copy (only sign-up forms freeze it).
- A merge drops pending sign-ups of the merged-away person (their link then grants nothing); a confirmed sign-up has no link to the person, so a merge needs nothing from it.
- Sign-up counts are totals per form; there is no per-list or per-day breakdown, and no export.
- Wording versions: forms are saved with `newsletter-consent-v1`, shown read-only. Since 0135 a sign-up records `newsletter-consent-v2` (v1 plus the link-clicks line) while the ministry counts link clicks; see `newsletter-consent-v2-automation-clicks.md`. Moving a form to another stored wording is not built.
- The embed height is fixed at 520 px; a resize message from the frame is not built.
- Rate limits are the existing hosted-form numbers; the production design still needs the founder decisions already open in the hosted forms record.
