# Social provider integration layer: acceptance record

Branch `zernio-integration-layer`, migration **0049** (`0049_social_integration`; 0047 is claimed by PR #81 and 0048 by a parallel HC-13 PR, so the snapshot chain's `prevId` must be re-pointed to whichever of those merges first before this one merges). Server, database, API and tests only: **no screen, component or user-facing copy.** Zernio is the API provider only; none of its frontend code is used.

## What changed

* **Port** (`src/server/social/port.ts`, `types.ts`): `SocialProvider` (accounts, health, publish/schedule, cancel, status, conversations/messages/comments read, webhook verify and parse) and a separate `SocialSender` (message and comment reply, signatures only). Harvest-owned domain types; a closed error set that never carries bodies or tokens.
* **Adapters**: `FakeProvider` (in-memory, deterministic, failure injection, idempotency) and `ZernioAdapter` (documented HTTP shapes, injectable `fetch`, backoff and `Retry-After`, `Idempotency-Key`, fixed error mapping). `ZERNIO_LIVE_NETWORK = false`: with no injected fetch it throws `DISABLED` before any request.
* **Kill switch**: `SOCIAL_INTEGRATION_ENABLED = false` in `registry.ts`. While false, every social route and the webhook give the same unavailable answer; the registry builds only the disabled adapter and hands out no sender.
* **Credentials**: sealed AES-256-GCM envelopes (`credential-envelope.ts`) under the key provider, new purposes `social-credential:v1` and `social-webhook:v1`; AAD binds tenant and connection; key id recorded. No plaintext in rows, audit, errors or logs.
* **Schema** (`0049`): `social_connections`, `social_posts`, `social_webhook_events`. FORCE RLS; connections and posts owner/admin only in SQL as well as in the service; owner policies for the definers; no DELETE grants. Triggers: connection identity and terminal `revoked`; post state machine (legal moves, terminal `published`/`cancelled`, frozen content, immutable provider reference, no unsafe retry); webhook rows append-only. Definers: `social_resolve_account` (web role), `social_publish_claim` and `social_publish_complete` (worker role only, granted when the role exists).
* **Permissions**: `social:connect`, `social:schedule`, `social:inbox`, owner/admin only, unknown roles denied. Audit rows hold ids and fixed states.
* **Service and API** (`service.ts`, routes under `/api/workspaces/[tenantId]/social/...`): link/list/enable/disable/health-check connections; create, schedule, reschedule, cancel, retry, list posts. A connection can only be created for an account the provider returns under the supplied credential, and one live provider account belongs to one ministry.
* **Webhook** (`POST /api/integrations/social/webhook/[provider]`): bounded body, constant-time HMAC over the raw body (current and retired derived secrets), tenant from our own connection record via the definer, age window, replay protection by event id, outbox plus job (`social.webhook`) that applies post results and account disconnects. One uniform refusal; one uniform acknowledgement. Message and comment text, sender names and similar are dropped at parse time and never stored.
* **Posting worker** (`publisher.ts`, `scripts/run-social-publisher.ts`): runs as `harvest_worker` with no table privileges; provider call outside any transaction; test mode only, local database only, FakeProvider only. At-most-once: same idempotency key on every attempt, crashed claims retried only inside 23 hours of the first attempt, ambiguous outcomes failed for a person, accepted posts reconciled by status and never republished.
* **Source guards** (`scripts/source-guards.ts`, wired into `scripts/check-source.ts`): vendor host, client import and adapter import confined to the adapter and registry; sending entry points confined to the port and adapters; no environment reads or network calls in the layer; both constants asserted literal `false`. `tests/unit/connect-crypto-guard.test.ts` allow-lists exactly two new modules (credential envelope, webhook secret derivation).
* **Reused existing copy keys** for API errors (`workspaceUnavailable`, `checkTheSuppliedDetails`, `webhookUnavailable`, `thisRecordChangedReloadAndTryAgain`); no catalogue entry added. Revisit when UI copy is written.

## Tests

* Unit: port contract suite run against FakeProvider and ZernioAdapter-with-mock-fetch (same 10 cases each); adapter request shapes, error mapping (9 statuses plus network/timeout/bad body), retries and backoff, `Retry-After`, same idempotency key on every retry, no retry of sends, zero fetch calls when disabled; state machine and failure classification; envelope round trip, binding, tamper, rotation; webhook refusals byte-identical and DB-free; source guard (repository clean, constants false, every rule detects a seeded violation); permissions; migration snapshot chain.
* Integration (real PostgreSQL): RLS and role matrix (owner/admin allowed; member, viewer, other ministry denied at service and database); credentials never plaintext (every public table scanned, audit, errors, console logs); database state-machine legality; worker end to end against the fake (publish, retry/backoff, permanent failure, attempt cap, accepted then reconciled, crashed claim inside and outside the window, stale completion refused, disabled connection, unopenable credential); webhook intake (tenant resolution, replay, unknown account, stale events, bad signature, applying results, disconnect frees the account); worker-role privileges; the worker script's role and test-mode gates; restricted-owner path (`testDatabase({ migrationOwner: true })`, run as `tester`).

## What is NOT done

No UI or copy; no OAuth/connect flow; no inbox cache or inbox service; no reply sending, Auto-DMs or blog distribution (the consent gate, `mayContact` from PR #81, would apply and is referenced in docs only); no webhook endpoint registration or secret provisioning; no quota or per-ministry rate limiting; no retention purge for `social_webhook_events` (keep at least 30 days) or for post content; no credential-rotation job; no scheduled invocation of the worker; no media pipeline from R2 to provider-fetchable URLs. A revoked connection keeps its sealed envelope (purge TODO).

## Nothing can reach the provider

Two constants, both `false` and asserted by tests and source guards. The adapter makes no request without an injected fetch; only tests inject one. The worker script uses the in-memory fake and refuses anything but test mode on a local database. Integration tests spy on global `fetch` and fail on any use. No key, secret or account exists in the repository. Production activation is **not authorized**; merging does not authorize it.

## Notes for the reviewer and coordinator

* Wire shapes come from the provider's public documentation and are **unverified against a sandbox** (recorded as assumptions in the plan). In particular the post-event account location, the health payload and the comment/message list shapes.
* A 409 duplicate-content answer is treated as a failure (`PROVIDER_CONFLICT`), not as success, because with our own idempotency key it can only mean different, earlier content.
* Scheduling is Harvest-owned: the provider is always asked to publish now. Provider-side scheduling is an open decision.
* Local test runs here used the embedded PostgreSQL as `tester` (the shared local cluster was being altered by another session's suite).
