# Office Mail screen acceptance

Operations > Office > Email: the UI for each owner's or admin's own mailbox, on top of the merged Office server (PR #185, migration 0075) and following the Office email inbox design (`docs/superpowers/specs/2026-11-19-office-email-inbox-design.md`, PR #138). No server change, no migration, no new dependency. Nothing is activated: the gate is closed in production, sending and calendar writes stay hard-off, and all five HC-02 gates remain UNAPPROVED.

## Done

- **Route and gate.** `/workspaces/[tenantId]/mail`. The page answers 404 before any session work while the Office gate is closed (`requireOfficeScreens`, the same non-production and Communities rule as the Office routes). Owners and admins only (`office:mail`); members, viewers and non-members get the neutral access state. The sidebar link is the registry entry `mail`, no longer planned, behind the new `office` navigation feature (never reported in production) and `office:mail`.
- **Connection states** (`OfficeMail`, `MailConnect`). Not connected: the catalogue privacy notice (`Office.personalConnectionNotice`) is always on screen and one button per provider (the person's affirmative action) starts `startConnect` with the notice version. A hosted authorisation URL opens in a new tab and is held in memory only; the page polls `finishConnect` every 3 seconds until connected, failed or expired, with Cancel. Reconnect needed (or a legacy connection with no provider): the same panel with one provider button and Disconnect. Needs attention (connection not healthy): check again (`health`) and Disconnect. Each admin sees only their own connection: `GET` returns only that person's rows, and another admin's connection id answers one neutral 404.
- **Inbox** (`MailWorkspace`). Provider folders by name plus Drafts when the mailbox offers them; the Inbox opens first. Message list with the provider's own search (debounced, Enter searches at once, 300 characters, the query is never put in the URL), cursor paging that follows a non-null cursor even from an empty page, the partial-page notice, loading, empty, error and "temporarily unavailable" states with retry. Nothing is filtered locally, so a page is never shown as a complete result (this is why the kit's All and Unread tabs are not used).
- **Thread** (`MailThread`). Live pass-through: messages as plain text with From, To and time; an HTML-only message says its text is not available; a missing thread is a neutral state. Mail content lives in component state only, never in browser storage, the URL (only the opaque thread ref) or page metadata. Opening a thread marks it read in Harvest (never in the mailbox). Star and read/unread toggles use the server `marker` action (Harvest-only) and update the row.
- **Link to a person** (`PersonLink`). An explicit reference to an existing CRM contact through the CRM `RecordPicker` and the `marker` `contactId`; the chip shows the contact's name, links to the person and unlinks. No contact is created and no consent recorded.
- **Drafts** (`MailComposer`). New message and Reply (prefilled with the sender, `Re:` subject, focus in the body). Drafts live in the mailbox: Save draft uses `createDraft` (one request id per composer, so a retry cannot create a second draft) or `updateDraft` with the provider version, and a 409 is reported as "changed elsewhere", never overwritten. Drafts view lists and reopens drafts (`draft` loads the body and version for mailboxes that list without bodies); Delete asks first. Recipients are checked (valid addresses, at most 20) before any request. Leaving an unsaved composer asks first.
- **Shared inbox frame.** The three-pane layout is now `InboxFrame` (`src/components/inbox/inbox-frame.tsx`), extracted from the social Inbox, which consumes it too (behaviour unchanged, its e2e re-run). The mail folder pane takes over the sidebar through `useContextualSidebar` with the registry exit (`exitTo`), exactly like the social Inbox; with `HARVEST_SHELL_MODES=disabled` it stays inline from 1280px and opens in a sheet below.
- **Forms one slot higher.** In Operations > People, Forms (`crmForms`) now sits directly above Imports. Unit tests updated; the e2e link counts are unchanged and no e2e asserts the order.

## Hard-off and deferred

- **Send, reply-send, forward and review are never called.** The Send button is visible, disabled, described by a short notice ("Sending is not available yet. Your draft is kept in your mailbox."). The e2e records every Office request and asserts none of `reviewMail`, `sendMail` or the calendar writes is made. The server returns `disabled` for them (`OFFICE_MAIL_SEND_ENABLED`, `OFFICE_CALENDAR_WRITE_ENABLED`, `OFFICE_INTEGRATION_ENABLED` and `OFFICE_LIVE_NETWORK` remain literal `false`). Calendar and Files screens are not part of this PR.
- **Deferred by design.** Labels and a Starred or Unread filter (the server `threads` action filters by folder and search only; Harvest markers are local, so a filter would be a locally filtered page), archive or mark-read in the mailbox (no port capability), attachments, forward, sanitised HTML, multiple mailboxes, shared addresses, mail-to-CRM capture, Settings > Connections entry for Office, a push or poll refresh (on-demand only), account switcher.
- **Rule held.** No real provider call and no real message anywhere: the routes use the in-memory fake provider (`officeRouteDeps`), whose demo mailbox is one sample thread. Larger lists, partial pages, errors, reconnect and attention states are exercised through route interception in the e2e.

## Server gaps found (reported, nothing invented)

1. A thread summary carries only `ref`, `subject` and the Harvest `marker` from the fake provider; the live adapter also supplies `snippet` and the latest received and sent times. The UI renders both shapes (snippet and time shown when present). Sender and unread-in-mailbox are not available on a list row.
2. `createDraft` and `updateDraft` take only `{ to, subject, body }`: a reply draft cannot carry the provider thread reference, so a Reply is saved as a standalone draft with a `Re:` subject (the design says "preserve the provider thread link when supported").
3. `threads` has no label, unread or starred input, so those filters are hidden.
4. The fake provider seeds one thread, so list realism comes from stubs in the browser tests.
5. The Office client notice text is read from the catalogue key the server names; the notice version the server sends is passed back in `startConnect`.

## Reuse rationale

Reused: AppShell and the contextual sidebar slot (`useContextualSidebar`, `contextExit`, `exitTo`), the three-pane layout now shared with the social Inbox (`InboxFrame`, `useCollapsibleList`), `EmptyState`, `StatusBadge` (through the shared rows), `ConfirmDialog`, the CRM `RecordPicker`, Field, Input, Textarea, Alert, Skeleton, Spinner, the toast helper and the typed navigation registry. New and Office-specific: the connection lifecycle, the browser client, `MailList`, `MailFolders`, `MailThread`, `MailComposer`, `PersonLink`, `ProviderLogo`. No module-specific shell was written; the only abstraction introduced (`InboxFrame`) has two real consumers.

## Provenance

Source: the paid kit's mail app (`bumbmatei-sys/admin-dashboard` `apps/mail` at `1631106`). **No kit file is copied**; every Harvest file is **modelled on** the kit layout and written for Harvest (the kit app needs resizable panels, a template editor, Zustand and mock data, none of which the design allows). Measured with `scripts/ui-identical.sh` on 21 Nov 2026, Harvest file as denominator: `inbox-frame.tsx` 4 of 46 (8%), `mail-workspace.tsx` 6 of 142 (4%), `mail-list.tsx` 7 of 98 (7%), `mail-folders.tsx` 3 of 46 (6%), `mail-thread.tsx` 4 of 94 (4%), `mail-composer.tsx` 4 of 99 (4%), `mail-connect.tsx` 4 of 102 (3%), all import and boilerplate lines. Recorded in `src/lib/ui-provenance.ts` (`adminDashboardReferences`, checked by `tests/unit/ui-provenance.test.ts`) and `docs/ui-sources.md`. Gmail and Outlook marks are simplified, drawn for Harvest (Gmail from the Simple Icons outline, CC0-1.0) in `src/components/office/provider-logo.tsx` with colours in `src/lib/theme-registry.ts`; they remain their owners' trademarks and are used only to name the connected mailbox. Product names are kept out of the message catalogue (source guard).
