## Screen contract

The workspace routes below are under `/api/workspaces/[tenantId]/social`. Responses, including errors and polling responses, use `Cache-Control: private, no-store`. Owner and admin permissions are checked in the services and FORCE RLS. Missing and out-of-scope items use a neutral 404. Writes and POST queries check request origin. Keep provider content, live search text, and cursor tokens out of URLs, browser storage and telemetry.

| Route | Contract |
| --- | --- |
| `POST /inbox` | One aggregate. An empty object starts with all sources. Filters are `account`, `platform`, `kind`, `folder`, `assignee`, `label`, `status`, `note` and `snoozed`. Send `cursor` with identical filters for the next page. `search` optionally uses provider conversation search live. Each row carries a Harvest item ID, account, local state and live preview. |
| `GET /inbox/sidebar` | Folder counts, platform and account groups, labels, assignable owner/admin teammates, account health and `activityRevision`. `If-None-Match` can return 304. Counts describe discovered identities and local metadata. |
| `POST /inbox/metadata` | Search Harvest fields without provider calls. Accepts the aggregate filters and an optional `after` UUID. Returns 50 local results at a time. Open a result by Harvest item ID to load its content live. |
| `GET /inbox/items/:itemId/conversation` | First live conversation page, account state, message capabilities and reply eligibility. `POST` with `{ cursor }` continues. A provider listing-only mention may require advancing a lookup cursor before the matching result appears. |
| `PATCH /inbox/items/:itemId` | Send `{ version, change }`. Changes are `read`, `assign`, `status`, `label`, `star`, `snooze` and `linkContact`. Read markers mean **read in Harvest**. |
| `POST /inbox/bulk` | Send a shared `change` and up to 25 unique `{ id, version }` items. Read, assignment, status, label and star return ordered `updated`, `stale` or `unavailable` results. |
| `GET /inbox/items/:itemId/notes`, `POST /inbox/items/:itemId/notes` | List Harvest-authored notes and apply versioned `create`, `update` or `delete`. Use `itemVersion` plus the note's version when editing or deleting. Only the author can change an existing note. |
| `POST /inbox/labels` | Create, rename or archive a versioned ministry label. |
| `GET /inbox/saved-replies`, `POST /inbox/saved-replies` | List, create, edit or archive ministry templates. Variable names use `{{ name }}`. The client supplies each declared value explicitly. |
| `GET /inbox/accounts/:connectionId/hours`, `PATCH /inbox/accounts/:connectionId/hours` | Read or set the version, IANA timezone, non-overlapping weekly `{ day, start, end }` slots, and optional Harvest-authored `awayTemplate`. For a new record use version 0. |
| `POST /inbox/items/:itemId/reply-eligibility` | Test the mode and optional target `{ mode, targetRef }`. Use this when a comment or message target is selected and before submitting. |
| `POST /inbox/items/:itemId/replies` | Queue `{ id, mode, targetRef?, text?, fileId?, saved? }`. The client creates a UUID per intent and can resubmit that same request. A saved reply uses `{ id, version, variables }` in place of freeform text. The receipt contains IDs, state and timing. |
| `GET /inbox/items/:itemId/replies/:replyId` | Poll the author's reply receipt. `unknown` requires verification and carries no permission to send the same text again. `confirmed` records provider acceptance. |
| `POST /inbox/items/:itemId/follow-up` | Send the item `version` and a Harvest-authored CRM `task`. The task is attached to the explicitly linked existing contact if present. The existing CRM service checks the assignee and relationship permissions. |
| `GET /media`, `POST /media` | Read quota and warning levels, or create an upload. Pass the selected `destinations` with `connectionId`, `type`, optional `format`, and optional `use` of `attachment`, `cover` or `subtitle`. |

Folder keys are `all`, `unread`, `assigned`, `open`, `done`, `starred`, `mentions`, `comments` and `dms`. The DM folder includes story threads. Distinct account and kind identities remain distinct even if their provider strings match. Account status and per-source `partial` states such as delayed, denied and expired are separate from zero items. An account can remain visible in the sidebar when its inbox capability is unavailable.

### Pagination and polling

A response takes up to 12 source pages in groups of four, with at most 10 list entries per source page. Provider calls use request timeouts. The signed, encrypted aggregate cursor binds the actor, ministry, filter, authorization set and version, with independent position and backoff for each account and source. It expires after 15 minutes. Expiring scan rows store reader and item IDs for deduplication. A replay of the same page may return that page again, so key UI rows by item ID. A fresh scan can reflect intervening provider changes and the first page of each source is ordered with the other available rows. Slow and pending sources can contribute older or newer items on a later page.

Retain the last loaded list or pane on a transient failure. Follow `nextCursor` to continue the current scan. A delayed account stays in `partial` with its own retry timestamp. Respect `Retry-After` when all remaining sources are backing off. Treat a stale or expired cursor as a request to start a new scan. A completely unavailable source reports a state and stops its scan.

Poll the sidebar with the last ETag while visible and online. Start a fresh list or pane read on `activityRevision` changes and use a periodic fresh read for providers and events with limited webhook coverage. Pause polling while hidden or offline. Resume on focus or reconnect after any outstanding Retry-After. The UI may keep live content in current component memory for recovery. A signed webhook queues only event, connection and reference metadata. The handler validates the outbox receipt, advances already-known activity where applicable, and stamps the event once.

## Reply and data boundary

The worker claims only reply metadata with `harvest_worker`, obtains a one-shot dispatch authorization under current connection, membership and media locks, then calls the provider after the database transaction commits. Disable and revocation cancel queued or leased work. Once authorized for dispatch, a remote action may already be underway. The first-attempt timestamp and fingerprint are immutable. Retries are bounded, use the same idempotency key and respect provider backoff. Unknown outcomes are reconciled by positive evidence only, with three bounded checks. The fake provider can confirm by key. The documented vendor read contract exposes no client-key lookup, so an unresolved vendor outcome stays unknown.

The submitted text, attachments' URLs and rendered template variables are transient reply material. An in-process, bounded handoff is supplied to the injected fake worker. After process loss the same authenticated request can re-offer identical bytes while the receipt is queued, subject to its expiry and fingerprint. A hosted transient handoff topology and real sender integration require review before activation. The web process receives no sender or worker grants. Stored notes, saved reply templates and away templates are explicitly Harvest-authored. Development tests search the inbox tables, webhook events, jobs, outbox and audit for synthetic message-body canaries. Inbound events do not create CRM contacts or consent records.

## Posting media safety

Grouped publishing can mint fresh per-attempt equivalent HTTPS download URLs through the revocable posting-media endpoint. The configured default is **2 hours**. A shorter documented provider fetch window takes precedence when configured. A new attempt replaces the earlier grant. Cancelled drafts, terminal media-fetch failures, retired files, revoked connections and expired grants refuse new requests. The endpoint streams from storage and supports HEAD and byte ranges. The underlying object URL is never passed to the provider by this path. Bytes already delivered before cancellation or retirement cannot be recalled. The standard upload, part and download URL lifetimes remain in their existing storage adapter.

The Media Uploads guide documents **5 GB per file for the provider's own presign endpoint** and stricter platform limits. It documents a 5 GB cap and a four-minute copy deadline specifically for Google Drive imports. The Prepare Media endpoint has a separate 200 MB video limit and needs a Content-Length. Instagram documents three failed media fetch attempts in its example. The public Create Post and Media Uploads docs reviewed on 20 November give no general elapsed retry deadline or single download cap for a self-hosted HTTPS URL. Harvest therefore uses the two-hour default, a 4 GB ceiling, and the lower selected-destination limits from its media table. Provider-confirmed fetch limits and hosted large-file streaming remain open verification. [Media Uploads](https://docs.zernio.com/guides/media-uploads) · [Create Post](https://docs.zernio.com/posts/create-post) · [Instagram media errors](https://docs.zernio.com/platforms/instagram#common-errors) · [Generated Prepare Media contract](https://github.com/zernio-dev/zernio-node/blob/f98ece5fad2b1d07f4c328cb96cd87de52910997/src/generated/sdk.gen.ts#L24216)

A definite fetch failure surfaces as `MEDIA_FETCH_FAILED` and retries under the existing delivery attempt bound when the provider has no saved post. A saved failed provider post or an expired idempotency window uses the retry action to return a destination-specific new draft for review. A timeout or other ambiguous transport failure follows the existing unknown-delivery flow.

Upload sizes use decimal GB for the Harvest caps. Five unfinished files may reserve space per ministry. A 25 GB cap includes pending reservations and ready or quarantined storage. `warning` begins at 20 GB. The upload endpoint reports per-destination size and type warnings and refuses an upload when every selected destination rejects it. Uploads without a publish selection, including media staged for a human reply, use the general upload cap and are checked again at their actual destination. Multipart parts stay 32 MiB.

The cleanup worker takes up to 50 pending or uploaded intents at least 12 hours old. It protects active confirmation leases, referenced drafts and unfinished deliveries, and ready media. It aborts incomplete multipart uploads and deletes any stored object under the same file lock. A failed storage operation leaves the database record available for retry. The app role has no cleanup grants.

For authorized non-production use, the worker requires `HARVEST_SOCIAL_UPLOAD_CLEANUP_ENABLED=1` and an unprivileged `WORKER_DATABASE_URL`. The `check` mode does not open storage. `run` uses dedicated `SOCIAL_CLEANUP_S3_ENDPOINT`, `SOCIAL_CLEANUP_S3_BUCKET`, `SOCIAL_CLEANUP_S3_REGION`, `SOCIAL_CLEANUP_S3_ACCESS_KEY_ID` and `SOCIAL_CLEANUP_S3_SECRET_ACCESS_KEY`. Scope these credentials to object deletion and multipart abort for the permitted non-production upload prefix. Grant no read or write permission. The operator commands are `node --import tsx scripts/social-upload-cleanup.ts check` and `node --import tsx scripts/social-upload-cleanup.ts run`. Exit 1 plus either `{"event":"social_upload_cleanup_alert","reason":"failed"}` or `{"event":"social_upload_cleanup_alert","reason":"backlog"}` identifies a failure or due backlog. This PR installs no schedule.
