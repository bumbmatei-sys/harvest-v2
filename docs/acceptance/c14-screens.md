# C14 Events screens

Member and owner screens for the canonical Events server (PR #135, migration 0059). Builds only on what that server exposes: no server change, no migration, no new environment switch. Events stay gated by `eventsEnabled()` (not in production, Communities enabled); every Events page answers 404 before session work when it is off.

## What is built

| Screen | Route | Notes |
| --- | --- | --- |
| Community Events tab | `/communities/[slug]/events` | Upcoming list (grouped by day) or month calendar (`?view=calendar&month=YYYY-MM`). Cards show date, time in the event's own zone, seats left or Full, my response. The tab is enabled in the community shell. |
| Event detail | `/communities/[slug]/events/[eventId]` | Going and Not going, waitlist join, explicit seat claim, leave waitlist, add to calendar (`.ics` from the server), cancelled and ended states, join link. |
| Owner events | `/workspaces/[tenantId]/events` | Owners and admins; list or calendar including drafts; New event. Navigation entry "Events" (Operations, Workspace group), shown only when the server reports Events enabled. |
| Event form | `/workspaces/[tenantId]/events/new` and `/events/[eventId]` | Shared EditorShell and WizardLayout: Details, Schedule, Access (join link, capacity, one optional reminder lead time). Save, Publish, Cancel event (confirmation). Cancelled events are read-only. The new event's id is generated by the page so a retried save is the same event. |
| Roster | `/workspaces/[tenantId]/events/[eventId]/roster` | Name, response and whether the seat is still valid (Active or Lapsed); cards on phones; 100 per page with a Next link. Names come from the communities' member lists (the server returns ids only). |

## Behaviour that follows the server

- The join link is never in a page. The page requests it only when the member clicks Join online, and only offers the button inside the widest window the server allows (up to 24 hours before the start until the end, published events). The server decides the real window; any refusal is shown as "not available right now", never as a reason.
- A draft, a missing id, an id of another ministry and an id the viewer cannot see all end in the same 404 (spec compares a draft and a random id; a malformed id is also 404).
- Seats, Full, my response and "can claim" come from the server response; nothing is inferred. A full event offers Join waitlist instead of Going.
- Times are shown in the event's own time zone with the zone abbreviation; calendar maths runs on wall-clock dates in that zone.
- The owner form reads the join link back with the manager join preview, which the server answers only for owners and admins.

## Not built or not verified

- **Placing an event in a community has no screen.** The server exposes no placement writer: `community_event_links` is written only by the privileged owner connection, and the E01 notes assign it to C14, which would need a server operation. Until then an event is visible only to owners and admins, and members see it only once placed. The form has no "where it appears" control. Needs a server slice first.
- **No per-community filter.** The list API is ministry-scoped, so the Events tab of a community lists every event the member can see in that ministry, not only the ones placed in that community.
- **No place or address field.** The server stores a title, description, time zone, times, capacity, reminder and a join link only. In-person location can go in the description until the server has a field.
- **No per-event waitlist switch.** In the server the waitlist is always available for capacity-limited events (member opt-in, explicit claim). The form has no toggle for it.
- **Join window length is not editable or readable.** It cannot be read back, so the form never sends it (the server default of 30 minutes applies on every save).
- The "Maybe" response is supported by the server but not offered in the UI (going or not going, as specified); an existing Maybe is displayed.
- New events default to the UTC time zone (the server renders the page, so the browser zone is not known without a hydration mismatch); the owner picks the zone.
- Month calendar is server-driven per month (no drag, no week or day views, no create-by-click).
- Not verified: a real browser on a phone (only a 360 px viewport at device scale 2), screen readers, other locales (English catalogue only), production behaviour (Events 404 there), hosted environment, Neon, and the five HC-02 gates (unchanged, unapproved). The full integration suite and the full browser suite were not run; only the specs named above.
