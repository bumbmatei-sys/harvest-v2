## Founder answers (25 Nov), recorded in `docs/decisions/founder-decisions-2026-11.md`

1. Anyone with `campaigns:write` edits and finishes any open draft; the owner stays the creator; the version check stays. Server and RLS change (migration).
2. Invitations: pick an existing member, or enter an email (a matching email invites that member; otherwise an invitation that adds the person to the ministry with access to that campaign only once accepted). Must be accepted, pending and accepted shown to the owner, 14-day expiry, delivery synthetic and hard-off.
3. Optional cover image or logo in step 2, reusing the event cover picker (scanned files). Needs a server field.
4. AI Campaign Copilot card shown as "coming later", not a working toggle.
5. Conditional questions: only departments and tools adapt to the type.
6. A read route so the dashboard shows the finished draft's configuration.
7. Draft Connect sources are part of CW-08.
8. Checklist completion stored per item; derived items still tick themselves.

Built in PR 2 (migration 0106, `when` 1795594888689): shared open drafts (Q1) and the optional cover (Q3). Storage objects of replaced or abandoned covers are not deleted yet (the event cover cleanup worker covers events only); the files stay private and unreachable, and a cleanup job is a follow-up. The campaign carries `cover_file_id` and has a signed read route, but the campaign page does not show it until the CW-07 dashboard.

Built in PR 3 (migration 0110): departments and invitations (steps 4) and the tool cards (step 5). Step 4 saves the departments only; a person joins a department by accepting an invitation, never by being added. An invitation to an email that is not a member creates, on acceptance, a membership in the inert `campaign_guest` role: it holds no permission anywhere, so the person reads nothing else in the ministry. **The campaign-only screen that role is meant for does not exist yet** (CW-07 dashboard), so an accepted guest sees "You now have access to this campaign only" and nothing more until then. The accept link is the only place the token exists (its hash is stored); live delivery is a constant off switch, and outside production a test sink writes the link to the test mailbox file. Removing an accepted person from a department is not built.

Built in PR 4 (migration 0111): step 8 (review, edit links, blocked reasons, Finish once) and the setup checklist on the campaign page. Steps 6 and 7 still show "Soon", so Next from step 5 goes to the review and the review lists budget and registration as not available. Finish creates the campaign row only (row 35, materialising boards and the rest, is not built). Checklist completion is stored per item (who and when); two items tick themselves (every included department has an accepted leader; counseling has one); the other seven are ticked by hand because the things they describe (venues, budget, payments, registration forms, the response page, partner churches, outreach events) do not exist yet to be derived from.

Built in PR 5 (no migration): the campaign dashboard for people who can write campaigns (owners, admins, members), from a new read route over the finished draft. Read-only members still see the details card only, because the draft is not theirs to read. A campaign that was not created by the wizard shows its checklist and a note that there is no configuration. The cover shows above the title when the campaign has one; a campaign without a cover shows nothing there yet, which is the slot for the type-art placeholder (#248).

Built in PR 6 (no migration): step 7 and the draft response source. Finish does not create a registration form, community, follow-up or referral record: those options are stored as choices and shown in the review and on the dashboard. The one source it adds is the unpublished response QR link, through the same function path as the Connect links screen (`campaign_response_links`, FORCE RLS, owner/admin publishes there). Nothing is published, sent or collected from this step.

Effect on the plan: Q1 and Q3 both need a migration (draft read and edit policies, the discard guard trigger, a cover reference on the draft and the campaign), too large to fold into the screens PR. They ship as **PR 2, "wizard server: shared drafts and cover"**; PR 1 stays screens only for steps 1 to 3 and the cover field joins step 2 in PR 2. Q2 is **PR 3 (CW-05 server and steps 4 and 5)**. Q6 and Q8 belong to the CW-06 and CW-07 PRs. The rows above follow these answers.
