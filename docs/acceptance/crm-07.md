# CRM-07 acceptance record: contact association events with privacy and consent controls

Date: 2026-11-06. Scope: PRD v2.5 §5A.4 CRM-07: "Zernio/form/contact association events with privacy/consent controls". Activity from connected channels, forms and other touchpoints is linked to the right person (and optionally an organization). It is shown on their timelines and stored only while the person's consent for that purpose allows it.

**Not in scope:** email inbox sync, calendar sync, CRM-08, unrelated follow-ups.

## Decisions

1. **One ledger, no new history store.**
   - Each stored association is an `association.record` row in `audit_logs`, written with the content row and a `crm.association.recorded` outbox event in one transaction.
   - The content (summary and raw payload) lives in `crm_associations`, exactly as note text lives in `crm_notes`.
   - The timeline reads the ledger row and joins the content, so the cursor (`(created_at, id) < cursor`, 50 per page) and paging are unchanged.
2. **A new timeline kind.** `TimelineItem` gains `{ kind: "association" }`. It shows on the person's timeline and on the organization's timeline when one is linked. A person's timeline finds association ledger rows by the ledger's `contactId` **or** by the association row's current owner, so activity moved by a merge shows on the kept person without rewriting the append-only ledger. Deals do not take associations in this slice.
3. **Consent is per purpose, never bundled.**
   - The consent ledger has three CRM-07 purposes: `messaging`, `form_follow_up`, `newsletter`, each recorded separately with when and how.
   - An association needs an **effective** opt-in for its purpose:
     - any outstanding withdrawal for that purpose (on any channel, with no later grant on that channel on both clocks) wins;
     - otherwise a grant allows only while it is still the **latest event on its channel**. A later "unknown" on that channel replaces it, as on the record page (review S2).
   - Without that, nothing is stored: no content, no ledger row and no outbox event. The caller gets `{ stored: false, reason: "consent_missing" | "consent_withdrawn" }`.
   - `guard_crm_association` enforces the same rule in SQL and locks the person row, so a concurrent withdrawal serializes.
   - Withdrawing stops new associations; existing ones are kept (see follow-ups).
4. **Matching.** People by explicit id or tenant-unique normalized email, phone or handle (two people → 409, none → `no_match`; names never match). Organizations by id or normalized domain. The same `(source, externalId)` is idempotent.
5. **Security.**
   - `crm_associations`: `tenant_id`, composite FKs (person, organization, consent), ENABLE + FORCE RLS with a `harvest_app`-only policy.
   - The app gets SELECT and INSERT only. Only the erasure and merge definers change rows.
   - Services also filter `tenant_id` explicitly, including the new timeline subquery.
   - Definers (`erase_contact`, `merge_contacts`, `rollback_crm_import`) are SECURITY DEFINER with `search_path = pg_catalog, pg_temp` and `REVOKE ALL … FROM PUBLIC`.
6. **Erasure** (`erase_contact` in 0024):
   - deletes the person's associations;
   - scrubs (summary `''`, payload `{}`, `redacted_at`) every other association whose summary or raw payload contains the person's **email** (case-insensitive), **phone** (digits only, at least 7) or **social handle** (case-insensitive whole token, optional `@`; one-character handles only with `@`; review S1);
   - strips `contactId` from `association.*` ledger rows.
7. **Merge.** `merge_contacts` moves the merged person's associations to the kept person before erasing the merged person. The consent rows they reference move with the same ids. The move is counted as `activities` in the result, the audit metadata and the merge preview ("N logged activities"). The guard allows the move only for the merge definer with a matching `app.merge_source`, failing closed.
8. **Import rollback.** An imported person or organization that logged activity links to is kept (counted in `kept`). Before this, the new foreign keys made the whole rollback fail (review B1).
9. **UI** (shadcn only):
   - A **Contact permissions** card on the person page: one row per purpose with state, when and how. "Record opt-in" / "Record withdrawal" open the consent form preset to that purpose and to the channel of the deciding event, so an opt-in can clear a withdrawal recorded on another channel (review S3).
   - **Log activity**.
   - Association entries on person and organization timelines.
   - At least 44 px tap targets on mobile.
   - All copy in `messages/en.json`, with no vendor names and "Organizations" wording (guarded by `tests/unit/copy-rules.test.ts`). The CRM-06 import, export and merge copy that came with the merge was brought in line ("No organization matches…", export column "Organization"; imports still auto-map "Company" or "Organization" headers).

## Full-run browser failure (crm.spec.ts Sort menu): root cause

The earlier full run timed out in `crm.spec.ts` waiting for the "Added" sort option. It passed in isolation.

- **Cause:** the list's page links are plain anchors (shadcn `PaginationLink`), so "Page 2" is a full document load. Its server HTML shows "Showing 21–24 of 24" before React hydrates. The test clicked the Radix Sort trigger in that window. The click was lost and nothing retried it, so the test waited out its 7-minute timeout. Under load, hydration is slower, which is why only the full run hit it.
- **Reproduced deterministically:** with every `/_next/static/chunks/**` request held back, a minimal repro failed 2/2 and the unchanged `crm.spec.ts` failed with the identical error after 7.0 min. The fixed spec passed in 5.3 min under the same delay.
- **Fix:** `crm.spec.ts` waits for the shell's `data-hydrated="true"` after full loads before using client-only controls: after "Page 2", after the reload before the stale-write edit, and after the goto before the mobile edit. No product change was needed.

## Parked follow-ups

- **Adapter and public forms.** Neither exists on main yet. `recordAssociation` and `POST /crm/associations` are the contract they will call.
- **Withdrawal does not delete existing associations**, and a merge can move activity onto a kept person who has an outstanding withdrawal for that purpose (same rule). A "withdraw and delete" choice and payload retention need a product decision.
- Review nits, not fixed here:
  - **N1:** concurrent redelivery with the same external id can return 409 instead of `duplicate`. Fixed later, see `docs/acceptance/crm-soft-followups.md`.
  - **N2:** a withdrawal racing an insert surfaces as 500, not `consent_withdrawn`. Fixed later, see `docs/acceptance/crm-soft-followups.md`.
  - **N3:** phone matching over the whole payload's digits can over-redact (safe direction).
  - **N4:** identifiers dropped by a merge are not used to scrub other people's activity.
  - **N5:** an erased person's activity still shows on the organization timeline as "removed" (source, kind, purpose, actor, time; no text).
- **Phone text matching** compares the full international digits; a national-format number without the country code is not matched.
- **No deal associations**, and no editing or deleting of a single association by users.
- CRM-06 screenshots under `docs/screenshots/crm06/` predate the wording change and were not regenerated here.
