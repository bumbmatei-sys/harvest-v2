# Files screen acceptance

Operations > Office > Files: one Files screen for the ministry's own uploads (Harvest) and the signed-in owner's or admin's own connected drives (Google Drive, OneDrive), on top of the merged Office server (PR #185, migration 0075) and the existing workspace Files server. No server change, no migration, no new dependency, no navigation change. Nothing is activated: the Office gate is closed in production, everything that leaves the ministry stays hard-off, and all five HC-02 gates remain UNAPPROVED.

## Done

- **One screen, route unchanged.** `/workspaces/[tenantId]/files` is restyled to the new layout instead of adding a second Files page; the Files entry stays in Operations > Office (nav registry untouched, so no sidebar count or list changes). Business logic, permissions, scan states and routes of the Harvest source are unchanged: every role that could open Files still can; viewers still cannot upload; downloads, the public link, retry verification and "quarantined files are unavailable" behave as before.
- **Layout (founder design: Studio Admin file manager combined with the paid kit's file-manager screens).** Home: a row of folder cards on top, a Recent files table below, then the storage overview. Opening a folder, searching or "View all" switches to the list view with breadcrumbs (Files, then the source while more than one source is shown, then the folder path, or Search results) and the same table. Search and the source chips sit above both views. Upload (Harvest only) is a dialog; Sources (the person's drive connections) is a dialog. Cards below 768px stack through the shared `DataTable` card layout.
- **Three sources.** Harvest is always a source. Google Drive and OneDrive appear only when the person has a healthy files connection (`GET office`, personal and private per admin). A source filter (chips, `aria-pressed`) picks one source, any combination or All; an empty selection is All, picking every source is the same as All, and a selection that names a source that is no longer connected falls back to All. With only Harvest there are no chips at all.
- **Source marks.** While more than one source is shown, a very small mark (about 14 to 18 px) sits at the bottom right of every folder and file icon: the Harvest logo, the Google Drive mark or the OneDrive mark from the logo registry (`SourceLogo`, colours in `driveMarkColors`). With one source shown there is no mark. The accessible name carries the source: `Folder Photos, Google Drive` on folder cards and folder rows, `File agenda.txt, Google Drive` on file rows; a Source column repeats it as text from 1024px so colour or an icon is never the only signal. Same-named folders from different sources are separate cards and rows with separate keys, never merged.
- **Live drive listings.** The browser lists through the Office routes (`files` with `folderRef`, `search`, `cursor`), one request set per shown drive, aborting on change. Nothing is stored by Harvest or in browser storage; no file bytes reach the client. A non-null cursor is followed (Load more, with the source name while marks show) and rows are de-duplicated by reference; `partial` shows a notice; failed, `temporarily_unavailable`, `reconnect_needed`, `unavailable`, `disabled` and a 404 (missing folder or another person's connection) each have a neutral per-source alert, with Try again, and never hide the other sources. A connection that is not healthy is not a source; a notice points to Sources.
- **Harvest source.** Uploads are flat, so the folder cards group them by type (Images, Documents, Text), derived from the file type and not stored folders; a type with no files has no card. The storage overview shows only real numbers: the total bytes and file count of the Harvest uploads the list holds, split by type. No quota, no free-space figure, no provider storage numbers.
- **Preview.** A drive file's Preview calls the server `preview` action and opens the returned provider page (http or https only) in a new tab with `noopener`; when the server says unavailable (for example a file with no provider page) a toast says so. Folders open in place.
- **Connect and disconnect from the screen.** The Sources dialog shows the privacy notice (`Office.personalConnectionNotice`) before any choice, one button per provider (the affirmative action), the hosted-URL handoff held in memory and polled (`useConnectAttempt`, extracted from the Mail connect screen, which now uses it too), status, check again and Disconnect behind a confirmation (the server removes the connection and the links the person made; nothing in the drive changes).
- **Copy.** Concise, no routine helper text under fields, "ministry" not "workspace", no vendor names in the message catalogue (names are in code and the logo registry; the source guard passes).

## Hard-off and deferred

- **Hard-off, absent or disabled.** Provider download, share, upload and delete have no control on the screen and no client call; the e2e records every Office request and asserts only `files`, `preview`, `startConnect`, `finishConnect` and `disconnect` are ever made (never `downloadLink`, `picker`, `fileLink`, mail or calendar actions). The server returns `disabled` for what it blocks (`OFFICE_INTEGRATION_ENABLED`, `OFFICE_LIVE_NETWORK` and the write constants remain literal `false`). Upload from the dialog goes to Harvest only through the existing upload path and scan rules.
- **Deferred by design.** Linking a file to a CRM person from the screen (the server has `fileLink`; not part of this screen), the hosted picker for Drive accounts that need it (`picker`), file type and date filters, sorting controls, grid view, bulk selection, drag and drop, a push or poll refresh (on demand only), moving or renaming anything.
- **Rule held.** No real provider call: the routes use the in-memory fake provider (`officeRouteDeps`), whose demo drive is one file. Trees, paging, failures and a second drive come from route interception in the e2e.

## Server gaps found (reported, nothing invented)

1. **One files connection per admin, not one per provider.** `office_connection_personal_kind_idx` is unique on `(tenant_id, owner_user_id, kind)`, so a person can hold Google Drive or OneDrive, not both. The screen supports any number of connected drives (filter, marks, separate folders, per-source states are all built and tested with Google Drive and OneDrive together through stub connections), but with this server one admin sees at most Harvest plus one drive. Showing all three at once for one person needs a server and migration change (unique on kind and platform), which is outside this PR.
2. **No modified time on drive files.** `FileDetail` has `ref`, `name`, `kind`, `parentRef`, `mimeType`, `size` and `webUrl`, but no created or modified date, no folder item counts and no owner. Recent files therefore cannot interleave drive files by date: dated Harvest uploads come first (newest first), undated drive files follow in source order, each in the order the provider returned. The Added column and the type-based Harvest grouping are the only date and count data shown.
3. **No Harvest folder or aggregate endpoint.** Harvest uploads are flat and `listFiles` returns the latest 100. Folder cards and the storage overview are computed from those rows, and say "Counting the latest 100 files" once the list is full instead of passing the total off as complete. A true total needs a server aggregate.
4. **Search scope.** The server searches by name inside the given folder (or the connected root, which the fake provider treats as the whole drive); Harvest search is local over the loaded rows. Search is therefore per source, not a single ranked result.
5. **Fake provider breadth.** It seeds one root file and its picker is inline, so folders, paging and a second drive are exercised through route interception only.

## Merge and sort rules

Entries from different sources are never merged. Folders are ordered by source (Harvest first, then the connected drives in connection order) and by name within a source. Recent files are newest first among dated entries (Harvest uploads), then undated entries in source order, each keeping the provider's order. Inside a folder or a search, folders come first, then files by the same rule. Recent files shows the first eight; "View all" lists all folders and files of the shown sources.

## Reuse rationale

Reused: AppShell and the shell breadcrumb, `DataTable` (table and cards layouts, sort slot unused), `EmptyState`, `StatusBadge`, Card, Dialog, `ConfirmDialog`, Breadcrumb, Input, Alert, Skeleton, Spinner, the toast helper, the existing `UploadControl` (unchanged, now inside a dialog) and the Office browser client (`call`, now exported), `OfficeApiError`, `ProviderLogo`'s registry file and `theme-registry.ts`. New: `FilesScreen`, `FolderCards`, `FilesTable`, `EntryIcon`, `StorageOverview`, `SourceFilter`, `SourcesDialog`, `UploadDialog`, `useListings`, `filesApi`, the pure model `src/lib/files-screen.ts` and the shared `useConnectAttempt` hook (two real consumers: Mail connect and the Sources dialog). The old `FileList` is replaced by `FilesTable` (its catalogue strings are reused; unused keys removed) and `ui-showcase` now names the new consumer. No module-specific shell was written. The contextual-sidebar pattern used by Mail was not needed: the design has no folder pane, the source chips and breadcrumbs are in the page.

## Provenance

Source: the paid kit, admin-dashboard at `1631106`: `file-manager` (`page.tsx`, `summary-cards.tsx`, `table-recent-files.tsx`, `storage-overview-card.tsx`) and `apps/file-manager` (`file-manager.tsx`), plus `apps/mail/components/account-switcher.tsx` for the sources dialog. **No kit file is copied**; all six new files are **modelled on** the kit layout and written for Harvest, with 1% to 13% of lines identical (imports and boilerplate), measured with `scripts/ui-identical.sh` on 22 Nov 2026. Recorded in `src/lib/ui-provenance.ts` (`adminDashboardReferences`, checked by `tests/unit/ui-provenance.test.ts`) and `docs/ui-sources.md` ("Files screen"). The kit's transfer chart and upload activity are not used (no data), and chat-app has no file-manager block. The Google Drive and OneDrive marks are simplified marks drawn for Harvest and are **subject to brand-guideline review** exactly like the Gmail and Outlook marks of the Mail screen; they remain their owners' trademarks and are used only to name where a file lives.
