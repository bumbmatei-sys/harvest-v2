# HC-07 — Personal accounts, invitation delivery and one-use claims

Baseline: merged HC-05 PR #30, main `bbe21415d8faa74660c1a6ab91a5283bdecf3882`. This record covers the user-authorized bounded synthetic implementation. Final head, runtime results and independent review are recorded at delivery.

## Product contract

A new published `connect-intake-v2` preset can offer three independent, unchecked choices: pastoral follow-up, newsletter and an invitation to a personal Harvest account. Invitation-only requests work, and a shared email is collected once. Existing v1 presets/links/evidence keep their original two-purpose behavior. Settings changes create immutable versions and require new QR links.

The account belongs to the person across Harvest. It does not join the evangelizer's Organization or community, enroll in a course, create a CRM contact, buy a product or subscribe to a paid plan. Full personal onboarding/preferences remain HC-08. Craft's Future: Public courses and Discover, global free/paid catalog and products on Discover remain separate; HC-09–12 cover community discovery/membership. The personalized QR landing editor is the next separate task requested by Matei, not implemented here. The personal welcome preserves a safe link back to the originating QR page for that future integration.

Journey: optional invitation request → honest pending receipt → bounded dispatcher → email link → user-triggered secure continuation → existing email-code authentication → explicit claim or decline → personal welcome and profile/resources. Existing accounts use the same verified identity, with no automatic merge or Organization membership. Mismatch offers account switching without revealing the intended recipient. Continuing without linking leaves the invitation unconsumed; expired/replayed credentials cannot claim. Abandonment never blocks resources.

## Trust and persistence

Migration 0029 is additive and does not rewrite merged migrations. It extends the allowlisted source/submit/rights functions for v2 while preserving v1, and adds three FORCE-RLS tables with no direct application grants:

- `connect_invitations`: delivery generation, token hash, keyed recipient digest bound to that token (not a cross-response email lookup index), expiring encrypted delivery envelope, bounded issuance history and lease/retry metadata.
- `connect_invitation_flows`: hashed random browser continuation handles, bound to a generation and capped by invitation/response expiry.
- `response_account_claims`: one verified grant per response, bound to the authenticated user, with a ten-minute validity capped by response expiry. HC-06 must consume it once inside its later CRM-association transaction; HC-07 never sets `contact_id`, `associated_at` or association consumption.

The server validates synthetic contacts and proof, decrypts only within the restricted invitation service, and derives the recipient digest from the current verified user row under a share lock. Public HTTP never returns the encrypted envelope, recipient digest, internal response/tenant IDs or a decrypt capability. SQL contexts share the existing trusted-server/application-role boundary; GUCs are not independent protection against a compromised application server. Definers derive scope from strong credentials and use a fixed search path; owner policies cover exact lookups, tenant context or the bounded synthetic worker.

Response, purpose-specific evidence and invitation intent commit in one transaction. Same-request replay retains the original delivery generation. An invitation recovery receipt can request/resend or withdraw an invitation, but cannot verify identity. Confirming requires both the invitation continuation and a matching live verified account plus an explicit action. Claim tokens are 256 random bits, hashed for lookup, expire after ten minutes and are consumed atomically. A newer generation invalidates older tokens and flows.

Email links carry the opaque token in a fragment, never query/path data. The client captures and removes it from history before interaction and holds it only in per-page memory. Opening the link is read-only. A same-origin POST creates a random continuation handle stored in an HttpOnly, SameSite=Lax cookie (Secure over HTTPS); only its hash is persisted. Sign-in continuation accepts fixed internal destinations, not arbitrary callbacks. Flow cookies are removed after successful confirmation/decline. Personal routes are authenticated and no-store/no-referrer; token pages/APIs are no-store/no-referrer and excluded from indexing. The service worker does not cache navigations/APIs.

## Delivery, cancellation and expiry

The new dispatcher reuses queue backoff conventions but is separate from the existing transaction-only job handlers. It reserves/fences work in a committed transaction and performs external I/O outside the transaction. No owner identity is borrowed. Before dispatch and claim it rechecks source publication/rotation/expiry, pending retention, invitation purpose and generation. Wall-clock checks run after lock waits.

The request timeout is twenty seconds, shorter than the one-minute lease; an AbortSignal reaches the real adapter. Retries use the same generation/token/provider idempotency key. A lease expiry is not proof a provider failed. Unexpired running work and attempted queued/failed work cannot be superseded by manual resend; reconciliation retries keep their generation until confirmed success or token expiry. An uncooperative transport or already accepted email cannot be recalled, so no stronger cancellation/delivery guarantee is claimed. The real adapter remains disabled and no actual provider behavior was certified here.

Receipt → source → response → invitation is the capability lock order. Legacy erasers/withdrawals already holding the response use a nonblocking receipt lock and fail atomically with retryable 40001 on contention. Erasure and account-purpose withdrawal delete invitations, encrypted envelopes, flows and verified grants through the canonical rights paths. Withdrawing newsletter or follow-up leaves account permission intact. Once a provider has accepted a message, rights invalidate its link; they cannot retract the message.

Purge takes the same receipt lock, re-reads the current invitation under a parent row lock and rechecks current expiry/generation before mutation, preventing stale purge candidates from clearing a concurrent resend. Expired envelopes/flows/grants are cleaned in bounded batches. Minimal issuance metadata remains for rolling resend limits for up to 24 hours, or until earlier response erasure/purge; this linkability remains part of the unapproved activation review. Resends use the existing authentication issuance bounds: sixty-second cooldown, five/hour and twenty/day. Public request/prepare paths also have persistent synthetic request quotas. These are test bounds, not approved production venue/abuse policy.

## Local operation and hard activation boundary

Normal development and production do not enable intake or invitation sending. The existing nonproduction + explicit synthetic mode + localhost disposable `harvest_test[_...]` DB + disposable test key checks remain mandatory. Only fabricated `example.test` contacts are accepted. Production intake is unconditionally disabled.

The real adapter integrates the existing email service and provider idempotency/abort options, but `CONNECT_INVITATION_LIVE_DELIVERY=false` is a source-level hard stop before reading credentials or calling a provider. There is no environment switch that activates it. A separate reviewed activation change is required.

`npm run connect:drain:test` is an explicit bounded local mock operator. It requires the actual `harvest_app` role, synthetic test environment, local auth origin and `HARVEST_CONNECT_TEST_MAILBOX`; it writes mocked messages to that local file and closes its pool. It cannot send to a provider. `npm run connect:purge:test` also purges invitation expiry state. No production schedule is deployed. Browser fixtures write disposable worker configuration only to their private temporary mailbox companion file.

All five HC-02 activation decisions remain UNAPPROVED. No live collection, legal notices, production key lifecycle, retention maximum/scheduler, provider sends, merge or deployment are approved by this slice.
