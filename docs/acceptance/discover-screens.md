# Discover screens: PRD to screen checklist

Screens for the Discover server (#234, migration 0100) and the Harvest staff role and review routes (#238, migration 0103). **No migration and no server change** in this work: every screen calls the routes that already exist. Hard-off exactly as the server is: the unified routes and these screens open only inside the non-production gate (`discoverGateOpen`, which needs `DISCOVER_SERVER_ENABLED` to be switched by a separate reviewed change for production). When the gate is closed `/discover` renders the legacy communities-only page unchanged, the owner and staff pages answer the neutral 404 and the sidebar row stays hidden. The five HC-02 gates stay UNAPPROVED. Nothing here approves deployment or activation.

Sources read: `CLAUDE.md`; `docs/prd/harvest-communities.md` section 8A (routes, filters, who decides, cards, destination pages, APIs, acceptance criteria 1 to 8) and section 6 (visibility); `docs/prd/public-mode-social-discover-navigation.md` section 3 (Discover is a marketplace, the sidebar row opens the ministry's own view); `docs/acceptance/discover-server.md`; `docs/acceptance/platform-staff-discover.md`; `docs/decisions/founder-decisions-2026-11.md` (staff and approval, 25 Nov); `docs/design-system.md`; `docs/plans/studio-admin-adoption.md`; `docs/plans/shadcnuikit-adoption.md`; `docs/ui-sources.md`; `src/lib/ui-provenance.ts`; the server code (`src/server/discover/*`, `src/server/platform/*`, `src/lib/discover.ts`) and the navigation registry entry `discover` (status `planned`, path `/discover/manage`).

Founder decisions applied (25 Nov): approval before listing at launch (a listing is public only when published, listed, opted in and approved for exactly its current public fields); Harvest staff are granted only by the ops script (no grant UI); staff routes need a sign-in within 15 minutes and answer a neutral 404 to everyone else. Founder-approved kit items (25 Nov): see "Kit items" below.

Status values: BUILT, STACKED (built in the second PR, which stacks on this one), DEFERRED (with the reason), GAP (needs a decision or a server change, recorded not guessed). Evidence names the code and the browser test; screenshots are in `docs/screenshots/discover/` (file names below). Delivery is split into two stacked draft PRs: public screens and owner screens first, the staff queue second (S1 to S12).

## Open questions

1. Public pages for courses and products (P8): where do they live (`/catalog/:slug`, `/courses/:slug`, `/products/:slug`)? Until decided, cards for them open the quick look only.
2. Names in report rows (S10): accept a migration to `platform_discover_reports`, or keep matching against the approved queue?
3. Course and product settings screens (O2): none exist; My listings hosts their List in Discover card for now.
4. Staff sign-in (S2): the re-auth prompt links to the normal sign-in page; a dedicated step-up flow is not built (`platform-staff-discover.md` #10, deferred).
5. Queue paging (S3): `GET /api/platform/discover/queue` returns the oldest 25 per state (the database function takes up to 100 but the route does not pass a limit or an offset). Approved listings beyond the first 25 cannot be reached to suspend them. Ask for a `limit` and cursor on the queue and report routes before launch volume.
6. Product browser coverage: a product needs an uploaded file to publish, which the browser tests do not seed; the product path shares the course components and server code and is covered by the server integration tests and the type tab's empty state, not by a product card in the browser.
