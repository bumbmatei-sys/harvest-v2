# Follow-up cases and counselor assignment (HC-13, server side)

Migration `0048_followup_cases`. Database, server and API only: no screens and no new user-facing copy (the founder is replacing the UI kit; errors reuse existing catalogue messages and carry a machine `details.reason`). Plan and the full list of open decisions: `docs/plans/hc-13-follow-up-cases.md`.

**Approves nothing.** The five HC-02 activation decisions, including HC-DEC2 (pending metadata access) and HC-DEC3/HC-DEC4 (tombstones, retention), stay UNAPPROVED (`docs/decisions/hc-02-activation-gates.md`). The feature sends no message and adds no sender or consent gate. Real collection, real invitation delivery and deployment stay hard-disabled: a case can only exist for a response that was verified and associated through the HC-05/HC-07/HC-06 path, which production keeps disabled.

## What changed

- `followup_cases` (0048): one row per `(tenant, response)` (HC-06's request key), holding ids, a state and timestamps only. No name, contact method, free text, notes or consent detail. The case id is random and unrelated to the response id. Composite foreign keys tie it to the ministry's campaign, response, contact and (assignee) membership.
- State machine, in the database (`followup_case_transition_allowed`, guard trigger) and mirrored in `src/lib/follow-up-cases.ts` (a test compares the two): `requested -> awaiting_assignment -> assigned -> attempted -> connected -> closed`, with `no_response` (retry, requeue or close), reassignment (`assigned -> assigned`), unassignment (back to `awaiting_assignment`) and `withdrawn` from any non-terminal state. `closed` and `withdrawn` are terminal.
- Access, enforced by RLS and definers (not only the service). FORCE RLS; the application role has a read-only policy (owner/admin: every case in the ministry; role `member`: only open cases assigned to them) and a column grant of the minimal columns (`id, state, contact_id, assignee_id, version, timestamps`). `campaign_id` and `response_id` are unreadable by the application role. No INSERT/UPDATE/DELETE grant. Writes go through three SECURITY DEFINER functions (`search_path = pg_catalog, pg_temp`, revoked from PUBLIC, granted to the application role): `open_eligible_followup_cases`, `assign_followup_case`, `transition_followup_case`.
- Permission keys `followup:manage` (owner/admin) and `followup:work` (owner/admin/member) in `src/lib/permissions.ts`; unknown roles are denied by the existing fall-through. `followup:work` alone grants no case: the database requires the assignment.
- Hooks on existing tables (definer functions, no change to `erase_contact`, `merge_contacts` or the retention sweep): a response scrub deletes its case (contact erasure, response erasure, subject rights and retention expiry all go through the scrub); an explicit merge moves the case with the response; demotion to viewer or removal of a member returns their `assigned`/`attempted` cases to `awaiting_assignment` and clears the assignee elsewhere.
- Service `src/server/follow-up-cases.ts` and routes under `/api/workspaces/[tenantId]/followup-cases` (`GET`, `POST`) and `.../[caseId]` (`GET`, `PATCH`). Lists are bounded and keyset-paged (default 50, at most 200, oldest first, microsecond-exact cursor, stable with tied timestamps) and return no total.

### Permission matrix

| Actor | Open cases | List/read | Assign/unassign | Transition |
| --- | --- | --- | --- | --- |
| owner, admin | yes | every case | yes (to an owner, admin or member of the ministry) | any legal move, including `withdrawn` |
| member assigned to the case | no | own open cases | no | `assigned->attempted`, `attempted->connected`, `attempted->no_response`, `no_response->attempted`, `connected->closed` |
| member not assigned | no | none | no | none |
| viewer, non-member, other ministry | no | none | no | none |
| anonymous | 401 | 401 | 401 | 401 |

All denials share one 403 body. Owners/admins get 404 for an unknown case id; a member gets the same 403 for an unknown id as for someone else's case. A counselor loses sight of a case the moment it is reassigned, closed, withdrawn, or they are demoted or removed.

### Audit

`followup.case.open`, `.assign`, `.unassign`, `.transition` and `.revoke` (system unassignment): target = case id; metadata only `from`, `to`, `assignee`, `previousAssignee` (user ids and states). Written in the same transaction as the change. No contact, response, campaign or free text. Rows survive a case's deletion and carry nothing that links to the person.

### Consent

Opening, assigning/reassigning and moving a case to `attempted` are refused while follow-up is not in effect: the response's own grant must be unwithdrawn **and** the CRM ledger's effective state for that contact, purpose and channel must be granted (HC-06: "a response and a CRM withdrawal must agree before any assigner acts"). Recording a withdrawal on a case (`withdrawn`) stays possible. Nothing here sends a message.

## What is NOT done

- No UI, notifications, SLA or reminders, language/timezone/workload matching, attempt channel/disposition capture, counseling notes, safeguarding escalation or per-campaign coordinator roles.
- No automatic case creation at claim time: owners/admins open cases (`POST .../followup-cases`). No automatic withdrawal propagation from consent withdrawal into cases (HC-14); staff set `withdrawn`.
- No church referral (HC-18), no aggregates or small-group suppression for case counts (HC-15), no read auditing (only changes are audited).
- No link between cases and CRM tasks/notes (deliberate; see decision 9 in the plan).
- A per-campaign queue filter is not offered: `campaign_id` is hidden from the application role so counselors cannot learn campaign participation. A manager-only projection would be a small follow-up if the new UI needs it.
- The ordinary CRM permission model still lets every ministry role (including viewers) read every contact, so a case limits what a counselor learns about the *case*, not about the *person*. This is the PRD's "minimal details for their assignment only" gap and needs a CRM visibility decision.
- `drizzle/meta/_journal.json` skips `0047`, which open PR #81 (HC-DEC1b) claims. When #81 merges first, the 0048 snapshot's `prevId` must be re-chained to the 0047 snapshot (it adds no schema change, so only `prevId` changes).
