## What ran locally

- The workerd probe dispatched matching cron names through the Harvest job port with a fake runner and exercised both hard-off handlers. Every registry entry refused execution with production settings, including when the probe explicitly selected the job. The listed schedules are proposed UTC schedules.
- The probe ran the consumer with an in-memory queue and with Miniflare’s local Queue bindings. Repeated deliveries of the same job and scheduled time recorded one receipt and ran the retention sweep once. A malformed message containing an extra field went to the dead-letter queue with a fixed reason and no original payload. A failing or busy delivery backed off for 15, 30, 60 and 120 seconds in the deterministic check, then went to dead letter on the fifth attempt. Failed dead-letter publication requested a retry. The probe also checked that a poison item did not block an adjacent valid item.
- A restricted migration owner installed the worker-only lease functions. The worker used a fresh CF-02 database scope per lease operation. The workerd lease probe used Miniflare’s Hyperdrive emulator and embedded PostgreSQL. An application credential in the worker binding, an app-only binding and a worker login with an elevated privilege were refused. Two contenders produced one holder, the holder renewed, and a later invocation recovered a lease after the test advanced its deadline past the database clock. The stale token could neither enter the write transaction nor complete the job after recovery.
- The retention port covers the HC-DEC3 and HC-DEC4 Connect sweep and erasure, the separate synthetic Connect intake and invitation purge, community chat retention, declined and withdrawn community applications, read community notifications and old email delivery records, and newsletter delivery retention. The workerd probe called the same port against the local fixture. The bounded community routines reuse the current age and state criteria and have worker-only execution grants. The Node variants keep their existing signatures and grants.
- With the existing social gate open for test mode, workerd ran grouped publish, inbox reply and analytics refresh using the existing fake provider. PostgreSQL recorded one published post, one confirmed reply and one analytics row. Redelivery made no further provider calls. The test checked both production indicators and verified that the test gate refuses the real adapter. The inbox probe supplied transient reply text in memory. Queue messages carried only a job name and scheduled time.

## How coordination works

A message is a wake-up for the existing domain tables and SQL claims. The delivery key is the pair of job name and scheduled time. A database lease serializes the job across slots, while completed receipts deduplicate each slot. The holder locks the lease row and checks its token and deadline in the same transaction as each protected write. Database-only jobs can commit their writes and receipt together. Social calls happen between short database scopes and retain the domain claims and reconciliation rules. A database fence protects commits. Provider effects need their own idempotency and reconciliation contract.

## Repeat the local checks

Use a Linux checkout with the repository lockfile dependencies and a disposable directory for the pinned tooling. The probe creates and removes its own embedded databases. It injects generated fixture values in memory and suppresses raw runtime output. The loopback guard applies to workerd and the probe. The fake jobs use a loopback connection binding for the existing local-only scope check. The lease and credential checks also exercise Miniflare’s local Hyperdrive binding.

```sh
npm ci
CF04_TOOLING="$(mktemp -d)"
npm install --prefix "$CF04_TOOLING" --no-audit --no-fund --ignore-scripts \
  miniflare@5.20261117.0-beta workerd@1.20261117.1
cc -x c -shared -fPIC spikes/cf-01/loopback.c.in -ldl -o "$CF04_TOOLING/loopback.so"
env -i PATH="$PATH" LANG=C.UTF-8 LC_ALL=C.UTF-8 \
  LD_PRELOAD="$CF04_TOOLING/loopback.so" CLOUDFLARE_CF_FETCH_ENABLED=false WRANGLER_SEND_METRICS=false \
  CF04_MINIFLARE_MODULE="$CF04_TOOLING/node_modules/miniflare/dist/src/index.js" \
  node --import tsx tests/cf04/run-local.ts
```

The scheduled probe is manual. The lease, restricted-owner migration, purge scope and Node advisory-lock checks run with the integration project. The Node job runner and newsletter send/dedupe tests continue to exercise their existing behavior.

## What needs staged evidence and a founder decision

- Authorize a protected synthetic staging test with an isolated database, a cache-disabled worker Hyperdrive configuration and fake providers. Verify the actual Cron event shape and timing, broker retries and dead-letter routing, and concurrent scope, disconnect and transaction behavior through real Hyperdrive. Verify redacted logs and resource limits at the same time. The local result covers job routing inside workerd and Miniflare’s broker, with the hosted control plane still to test.
- Choose the schedule, operator, alert thresholds, replay procedure and receipt retention period before enabling anything. Inspect the PostgreSQL job state and the dead-letter queue together before replaying. A dead-letter send can itself be delivered twice if the original acknowledgment is lost. Deduplicate terminal records by job and scheduled time. If the dead-letter producer is unavailable, a hosted broker fallback queue and retry cap still need configuration and testing.
- Decide how to rediscover committed outbox work when a queue publish fails. The current tenant-authorized Node drain, generic outbox reconciliation, newsletter delivery and community email remain on their existing paths. A future Worker drain needs a narrow service grant and a reconciliation check. Live social would also need proven provider idempotency, a durable inbox handoff that meets the product’s data rules, and review of ambiguous outcomes. Workflows remain deferred.
- Retention activation still needs approval of the policy and monitoring owner. Real providers, real-data activation, migration application outside fixtures, and the hosting cutover each require separate authorization.
