# Move Harvest to its new domain

1. Choose the app and marketing hostnames and a separate staging app hostname. Decide which previous app hostnames must keep resolving because QR codes, invitation links or emails already use them. Keep control of those hostnames and their TLS certificates during the transition.
2. Prepare staging first. In Cloudflare, attach the staging hostname to the staging app as a Custom Domain when the app is hosted on Workers. For an external app or marketing host, add the CNAME that the hosting service specifies, or its A/AAAA records if it supplies IP addresses. Check that the DNS record, TLS certificate and hosting binding refer to the same environment. Use Full (strict) where Cloudflare proxies to an HTTPS origin. Keep the existing live records while staging is being checked.
3. Set the environment values below on staging. Use full origins with a scheme and hostname, with no path, query or fragment. Use distinct staging credentials and existing staging isolation. Leave the optional settings empty on the first pass.

   | Setting | Value |
   | --- | --- |
   | `BETTER_AUTH_URL` | The app origin in this environment. |
   | `MARKETING_ORIGIN` | The separate marketing origin if there is one. Defaults to the app origin. |
   | `HARVEST_PRODUCTION_ORIGIN` | On Workers, the designated production app origin. Staging, preview and local must use a different app origin. |
   | `LEGACY_ORIGINS` | Comma-separated old app origins. Empty is the default. |
   | `AUTH_COOKIE_DOMAIN` | Leave empty for host-only sign-in cookies. Set a shared parent domain only after deciding that both hosts belong in the same cookie trust boundary. |
   | `HARVEST_NEWSLETTER_ORIGIN` | Retain only if an existing dedicated newsletter link origin still needs to serve those routes. Otherwise newsletter links use the app origin. |

   Configure sign-in on the app origin only. The marketing origin is for the separately hosted marketing site. Existing Harvest routes such as blog, giving and community pages are served by the app. Remove any extra `BETTER_AUTH_TRUSTED_ORIGINS` entries before changing the app address. Existing cookies on the old host may require users to sign in again after switching.
4. Prepare email. Keep sign-in mail on its current sender and verify the new From domain with that sender. Put its verified mailbox in the existing `EMAIL_FROM` setting when the change is separately authorized. Verify the new community and newsletter sending identity in Amazon SES in the planned region, using the instructions generated for that identity. Add each provider's DKIM records, and publish the SPF mechanism for each sending domain at the DNS name supplied by the provider. If SES uses a custom MAIL FROM subdomain, publish its requested MX and SPF records there. Consolidate SPF mechanisms into one SPF TXT record per DNS name. Publish DMARC at the appropriate `_dmarc` name, using the agreed policy and report mailbox. Keep verification CNAMEs DNS-only. Check SPF, DKIM and DMARC alignment before authorizing any real sending. Use synthetic addresses and a test mailbox for the staging flow.
5. Configure redirects after testing the new app origin. Bind the old hostnames to a service that can serve their HTTPS requests and set `LEGACY_ORIGINS`. The app gives GET and HEAD requests a 301 to the same path and query on the app origin. Test a previously generated short link, QR URL, invitation path, unsubscribe link and a page with repeated query parameters. Confirm the app writes and signs new links using its configured origin.
6. Keep callback endpoints reachable at their registered hostname during cutover. The redirect skips `/api/auth` and its children because auth callback URLs and cookies are origin-scoped. It skips `/api/integrations` and its children and `/api/newsletter/callback` because external integrations can depend on the exact registered endpoint and body. It skips `/api/files/transfer` because storage grants bind to the issuing origin. All non-GET/HEAD requests skip the 301, including the signed one-click POSTs to `/api/newsletter/unsubscribe` and `/api/communities/unsubscribe`. Where an existing grant or auth callback still needs old runtime settings, keep the old handler on its issuing origin until it expires or drains. Register new callback URLs with their providers as a separately authorized step and verify the old paths still reach the original handler during the overlap.
7. Roll back by removing the legacy origins from configuration, restoring the prior app and production-origin values, and restoring the old hosting bindings and DNS records. Restore the prior mail From domain if it changed. Keep both endpoints reachable while DNS and certificates settle. Browsers and intermediaries may retain cached 301s, so keep the new host serving the app during rollback and avoid adding a reverse permanent redirect.
