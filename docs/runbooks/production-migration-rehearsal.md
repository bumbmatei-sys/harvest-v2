# Production migration rehearsal (QA-4)

The rehearsal models a database with migrations through 0030 applied. The [production migrations runbook](../setup/production-migrations.md) and [Neon setup record](../setup/neon.md) require checking the actual applied journal before a rollout. No live connection is needed for QA-4.

Run **Production migration rehearsal (QA-4)** manually in GitHub Actions and download the `migration-rehearsal` artifact. For a local run, create the `harvest_rehearsal` maintenance database in a disposable loopback PostgreSQL 17 instance. Set `REHEARSAL_DATABASE_URL` to that database with an explicit port and its local provisioner login, then run `npx --no-install tsx scripts/rehearse-migrations.ts`. The script creates and drops a separate uniquely named database. It seeds two synthetic ministries at 0030, applies the pending journal in one transaction as a non-bypass migration owner, and prints a compact report. Lock durations are sampled lower bounds. The report counts all sampled locks over five seconds and lists the longest held and waiting locks. Locks can be retained across migrations until the batch commits. A synthetic dataset measures rehearsal behavior on that dataset.

## Approved rollout procedure

1. **Create a restore point first.** Record the verified restore branch or snapshot identifier, timestamp, and recovery owner before any schema writes. Record the actual production journal and the pending entries at the exact candidate commit. See the [production migrations runbook](../setup/production-migrations.md).
2. **Dry run on a copy.** Use an isolated, access-controlled copy of the recorded state. Disable jobs and outbound integrations. Run the exact candidate migrations as the restricted migration owner, retain timings and lock evidence, and verify RLS, worker grants, data invariants, and definer ownership. Compare the results with the synthetic rehearsal.
3. **Get the founder's approval and apply in one batch.** Record the exact commit, target, restore point, window, and reviewed evidence. Use the separately authorized production migration procedure with the direct owner connection. Pause writes as agreed for the window and retain the migration result.
4. **Verify before releasing traffic.** Compare the full applied journal to the candidate. Verify forced RLS, scoped access, worker-only execution and no worker table grants, definer ownership and search paths, and the expected backfills. Run the approved smoke checks and record outcomes.
5. **Roll back if needed.** If the batch fails, confirm PostgreSQL rolled it back and the previous journal and application checks still pass. If verification fails after commit, hold writes, preserve evidence, and assess a forward fix with the founder. Before restoring, account for writes since the restore point and get approval for the restore and reconciliation. Restore into an isolated target first, verify the previous journal, access controls and data, then switch back under the approved recovery plan. Keep the restore point through sign-off.
