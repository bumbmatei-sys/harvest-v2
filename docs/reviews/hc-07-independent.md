## Scope and conclusions

The review read AGENTS.md, CLAUDE.md, the full Harvest Connect PRD, HC-02/HC-05 acceptance, HC-07 acceptance, and all final implementation/test/documentation deltas. Particular attention covered security-definer ownership, FORCE RLS, SQL rights hooks and races, provider ambiguity, cryptographic bindings, browser credentials, authentication destinations and migration compatibility.

- **Purpose and product separation:** v2 adds an independent unchecked account-invitation choice, including invitation-only requests and combinations using one email. Legacy v1 purpose restrictions remain. Published definitions/evidence are not rewritten. No Organization/community membership, paid plan, product purchase, course enrollment or CRM association is created. Global Discovery and the personalized QR editor remain separate work.
- **Verified identity and claims:** 256-bit opaque tokens are hashed, expire after ten minutes, and require a separate random cookie-backed continuation, a live verified matching account and explicit confirmation. The server re-reads and share-locks the current user row rather than trusting verification/email fields supplied to the service. Consume rechecks generation, expiry, source and purpose under locks; one verified claim per response is enforced. Decline removes only the continuation. HC-06 must later consume the user-bound claim once within its association transaction.
- **Database boundary:** all three added tables enable and FORCE RLS, revoke direct application/PUBLIC privileges and use migration-owner policies. Public function EXECUTE defaults are revoked; callable definers have fixed search paths. Tenant scope comes from credentials and authoritative parents. This retains the documented trusted-server/application-role boundary: caller-controlled GUCs alone do not protect against a compromised application server. The restricted-owner test source installs the real migrations under a non-superuser, non-BYPASSRLS owner and exercises capabilities through `harvest_app`.
- **Credentials and browser handoff:** email tokens use fragments; the client removes the fragment before interaction and retains the token only in page memory. Opening a link does not consume it. Prepare/claim mutations check origin and bounded strict bodies. Continuations use HttpOnly, SameSite=Lax cookies, Secure under HTTPS, with only hashes stored in the database. Public HTTP does not expose encrypted envelopes, recipient hashes or internal tenant/response identifiers. Redirect destinations are fixed internal routes; QR return paths have an exact allowlist. Normal organizer sign-in remains unchanged; personal sign-in does not send a person into Organization setup.
- **Cryptography and rights:** delivery AAD binds the receipt and token hashes; the dispatcher checks the reserved-row bindings and decrypted token. Recipient HMACs are scoped to each token, avoiding a stable cross-response email digest. Account-purpose withdrawal and canonical erasure invalidate invitations, envelopes, flows and grants; other purpose withdrawals remain independent. Receipt/source/response/invitation locking and retryable legacy-erasure contention preserve atomic rights behavior.
- **Delivery boundary:** reservations commit before external I/O. Retries retain generation, token and provider idempotency key; stale leases cannot finalize newer work. The twenty-second deadline propagates an AbortSignal. Unexpired unsettled attempts cannot be superseded solely because a lease expired. The real adapter has a source-level `false` stop before credentials/provider calls; local operator delivery writes only a mock mailbox and requires the synthetic environment and actual application role.
- **Compatibility:** migration 0029 is additive, retains merged migrations and the existing table metadata, and extends allowlisted functions for v2. Existing v1 ciphertext format and rights behavior remain compatible. The personal profile reuses the existing profile service. The new schema/journal/snapshot are consistent on static inspection.
