Recorded 2026-11-05 for the People/Companies slice. These notes describe **behaviour** worth reproducing. ### Edge cases carried over from reading the code

- Whitespace-only edits become empty values, not stored spaces.
- Duplicate checks need at least three characters, so "Al" does not light up every "Al…" record.
- The current record is excluded from its own duplicate list.
- A relation picker must not offer records that are already linked.
- An empty filter result is a different state from an empty object, with a "reset view" action.

## Harvest v1 lessons applied

- **One CRM per tenant** (§6.4) remains true: People and Companies are workspace-scoped tables protected by forced RLS, not per-community lists.
- **Never match on admin-editable email alone** (§6.7). v1 learned that letting an email match clear a stranger's opt-out was unsafe. Harvest never merges on email or name. Normalized identifiers are unique per tenant and reject duplicates with a 409; same-name records are suggestions only.
- **Filters and exports must agree** (`crm-filter.ts` docblock). The People list computes the effective marketing state in SQL with the same rule as the consent ledger: an outstanding withdrawal wins unless a grant is strictly later on both clocks. The list filter, the list badge and the record page therefore agree. An integration test pins this, including a backdated grant. A bug where the badge and the filter disagreed was found and fixed during this work (see the acceptance record).
- **Hiding a button is not the security boundary** (§6.10). Every mutation is checked on the server (`companies:write` / `contacts:write`) and by RLS. The viewer UI also hides edit affordances.
- **Erasure deletes rather than hides** (§6.6). Erasure now also removes the person's company links and unlinks their link audit history, so no surviving row ties an organisation to the erased person.
- Not carried forward: Firestore document shapes, synthetic member contacts built from `users` documents, client-side filtering of whole collections, and v1 branding.

### Harvest v1 filter lesson (re-read)

`Harvest-agent/src/lib/crm-filter.ts`: one predicate is shared by the list and the export so they cannot disagree, and consent status is read from the consent fields rather than a legacy boolean. CRM-03 keeps that discipline: the "Email marketing" filter, the "Email subscribers / Unsubscribed / No email decision" system views and the list badge all compile to the single `marketingEmailState` SQL expression (withdrawal wins unless a grant is later on both clocks).

### Harvest v1 pipeline lesson

`Harvest-agent/src/components/AdminCRM.tsx`, with tests in `__tests__/AdminCRM.pipeline-stage.test.tsx`: v1's "pipeline" was a board of **contacts** whose stage was derived from total giving (`resolvePipelineStage`). A stored `stage` field drifted and had to be ignored, and the board deliberately had no mover. Lessons for CRM-04:

- Deals are separate records with an explicit stored stage, written only through the move or patch API.
- Never derive a deal stage from giving, or rank people by engagement (PRD §4.7: no coercive scoring).
- The board and the list read the same server query, so they cannot disagree.

### Harvest v1 lesson

`Harvest-agent/src/hooks/queries/useCRMQueries.ts` defines `ContactActivity` (types `note`, `donation`, `email`, `call`, `meeting`, each with a free-text `description`), and `AdminCRM.tsx` renders it per contact. v1 had **no task model** and no assignee. Its own comments document a bug (THE-350): donation amounts stored on activity rows duplicated the invoice record ("one gift in two money-bearing documents"). Lessons for CRM-05:

- Keep exactly one source of truth per fact. The timeline *reads* the audit ledger and notes and never copies amounts or other domain values into a second store.
- Tasks are first-class records with an owner (assignee) and audited history.
- Notifications go only to the person a task is assigned to.
- Free text (notes, task bodies) never leaves the database in outbox events.

### Harvest v1 lessons, applied

- `crm-filter.ts`: **one predicate for list and export.** CRM-06 builds the People export's `WHERE` with the same function as the list, including `marketingEmailState`. A test asserts that the list total and the export row count agree for each filter.
- `crm-merge.ts` and PRD §6.7: **an editable email must never clear an opt-out.** Imports never write consent events. "Fill empty fields" adds only missing identifiers, notes and company links, and never touches the consent ledger. A merge moves all consent events, so the effective state is recomputed from the full ledger, where any outstanding withdrawal wins.
