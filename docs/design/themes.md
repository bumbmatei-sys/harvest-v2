# Themes

`src/lib/theme-registry.ts` is the palette source for Harvest and Studio, with light and dark modes for each. It generates selectors for the application, appearance previews and public offline page. `src/app/globals.css` maps the registry variables onto semantic shadcn tokens such as `background`, `foreground`, `card`, `primary`, `destructive` and `sidebar`. Components use these tokens instead of literal colors or Tailwind palette classes.

To add a theme, add a complete light/dark definition to that one registry file and its display-name translation under `ThemeNames` in `messages/en.json`. The registry derives allowed theme IDs, validation and selectors. The current UI presents one baseline with System/Light/Dark mode controls. Components require no changes. Persistent workspace themes are constrained by PostgreSQL, so making a new theme selectable as a workspace default also requires an additive migration to the existing database constraint. Rebuild and regenerate the offline page, then run the registry and browser tests.

The user's validated local preference overrides the workspace default. Without a user mode preference, light/dark follows the system. A bootstrap script applies both axes before paint; controls follow storage and system changes. Invalid stored values fall back to the workspace or Harvest. Appearance changes require the existing server-side workspace permissions.

Phase 0A adopts Studio Admin’s neutral primary/hover colors and mode-specific `--action-foreground`. Existing Harvest/Studio preference IDs remain valid and both render this baseline; they do not currently offer distinct palettes. The previous exact palettes are preserved in `legacy-palettes.json` for a future optional-theme slice, with no database rewrite. Gold is not the default. Unit tests enforce at least 4.5:1 contrast for those pairs and key text/surface pairs; browser axe checks cover every main screen in all four variants.

`npm run lint` and source-guard unit tests reject raw hex, RGB/HSL/OKLCH values and Tailwind palette utilities outside the registry. The generated public CSS and image assets contain resolved colors by design. Browser tests additionally inspect rendered class names and inline styles and save synthetic-data screenshots and axe results to `docs/screenshots/pr03/`.

Phase 0A continuation: account/public controls now present System/Light/Dark rather than duplicate Harvest/Studio palette aliases. Those IDs remain compatible in storage and the workspace settings API; they are not rewritten on render. Choosing System removes the color-mode override and follows device changes, including when storage is blocked. `ThemePreviews` displays both modes using explicit local mode selectors, canonical components and inert decorative content. There are no preview writes, portals or new theme IDs. Additional palettes remain future work.

ThemeRuntime in the root layout owns the media/storage listener independently of sidebar visibility. This keeps System mode live with the mobile drawer closed; controls only observe the shared theme-change event.
