# ADR 0008: CRM custom fields, saved views and the validated filter language

Accepted 2026-11-05 for CRM-03 (PRD v2.5 §5A.4; companion PRD §5). Builds on [ADR 0007](0007-crm-companies-and-links.md).

## Context

People and Companies need tenant-defined fields, reusable list views, and filters that people can build without typing. They must not weaken tenant isolation, consent semantics or erasure. Twenty CRM was studied for behaviour only (AGPL-3.0; see [research notes](../research/twenty-crm-reference.md)).

## Decision

1. **Definitions** (`crm_field_definitions`, key `(tenant_id, id)`) belong to one object type (`person` or `company`). They hold a stable **key** (`^[a-z][a-z0-9_]{0,39}$`, unique per tenant and object), a label, a description, a type, a required flag, options, a relation target, a position and `archived_at`. The types are `text`, `number`, `date`, `boolean`, `select`, `multi_select` and `relation` (to a person or a company). Anything else is rejected by zod, by a CHECK and by the guard trigger. Key, type, object type and relation target are immutable (guard trigger, plus no column grant). Option values are immutable slugs, and labels may change. An option still used by a record cannot be removed (409). Archiving hides a field everywhere and keeps its values; restoring brings them back.
2. **Values** (`crm_field_values`) use one typed column per kind: text, double precision, date, boolean, `text[]` options, and one relation column per target. `num_nonnulls(...) = 1` enforces a single value. Composite tenant FKs point to the definition `(tenant_id, field_id, object_type)`, the record, and the related record, so a value can never cross tenants or object types. Partial unique indexes allow one value per record and field. A guard trigger re-checks the type, the allowed options, distinct multi-select values, a non-archived definition, a live (non-erased) person, immutable identity and `updated_by` provenance. Clearing a value deletes the row.
3. **Concurrency**: custom values are versioned by their **parent record** (`contacts.version` / `companies.version`). The client sends the version it saw; a mismatch is 409 `{ reason: "stale" }` with nothing changed. Built-in and custom inline edits share one version and one stale notice.
4. **Permissions**: values follow `contacts:write` / `companies:write`. Definitions need the new `crm:fields_write` (owner and admin only), because a schema change affects every member. Views can be saved by writers. Everyone with read access can read definitions, values and views. Viewers cannot mutate any of them (service and API tests).
5. **Saved views** (`crm_saved_views`) store `{ q, sort, filters, columns, density }` as strict JSON (at most 16 KB). `owner_user_id` is NULL for a workspace view and the creator for a personal view. RLS shows personal views to their owner only, enforced in the policy itself, with `app.user_id`. Another member's personal view is indistinguishable from a missing one (404). The **URL is the source of truth**: `?view=<id>` alone applies the stored state, and explicit parameters override it. Save as, Update, Delete and Reset are explicit actions. Nothing auto-saves.
6. **System views are code, not rows**: All people, Email subscribers, Unsubscribed, No email decision, No company; All companies, With people, No domain. They have `system:*` ids, read-only state, and names from messages. They need no seeding per tenant, cannot drift between tenants, and cannot be edited or deleted (403). "Email subscribers" and the others use the same effective-marketing SQL as the record page and the CRM-02 badge. *Deviation from "seed workspace default views": nothing is inserted per tenant; the result for users is the same.*
7. **Filters** are a small typed language: `field~operand~value` in the URL, `{ field, op, value }` in views. Each type has its operands (text: contains, does not contain, is, is not, empties; number: is, is not, at least, at most, empties; date: is, before, after, empties; boolean: is; select and multi-select: any of, none of, empties; relation: is, is not, empties). Built-in fields share the language (name, email, phone, company, marketing, created, updated; name, domain, people, created, updated). Every filter is validated against the tenant's **live** definitions and compiled to parameterized SQL. One unknown field, operand or value rejects the **whole** state (400 `invalid_view`). The page then shows the default view with a notice, never part of the view. CRM-02 shareable parameters (`company`, `email`, `marketing`, `people`, `domain`) are translated into filters.
8. **Columns**: Name is fixed first. The others are built-ins plus active custom fields, at most 20, each with a fixed width. Per-grid container-query rules show column *n* only when the card can hold Name's minimum plus columns 1…n, so the card never scrolls sideways at any sidebar state. A notice says how many columns are hidden. *Unknown or archived columns in a stored view are silently omitted* (unlike filters), because a missing column cannot change which records are shown.
9. **Grid keyboard model**: ARIA `grid` with a roving tabindex. Arrows move (right from the last column wraps to the next row), Home and End jump, Enter or F2 edits an editable cell, and Enter on Name opens the record. In the editor, Enter or blur commits, Tab commits and moves, and Escape cancels. Editable in the grid: email and phone (people), domain (companies), and custom text, number, date, boolean and select. Multi-select and relation values are edited on the record page.
10. **Erasure**: `erase_contact` (replaced in 0014) deletes the person's own custom values and any relation values pointing at them before re-keying. It removes saved-view filters that mention the person's id. Audit metadata for custom edits holds `cf:<key>` field names only.
11. **No outbox**: CRM-03 emits no CRM outbox events. Activity still reads the audit ledger only.

## Consequences

- A tenant can add up to 50 options per field. Required fields block clearing, but CRM-03 does not enforce them when records are created (record-create forms are unchanged). They are shown with a marker.
- Relative date operands (for example "in the last 30 days") are deferred. Filters combine with AND only.
- Migration 0013 is generated. Its composite FK needs the `(tenant_id, id, object_type)` unique index first, so that index statement was moved before the FKs by hand, with a comment. Migration 0014 is hand-written: policies, grants, triggers and the function.
