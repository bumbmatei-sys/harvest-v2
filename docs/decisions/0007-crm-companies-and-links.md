# ADR 0007: CRM companies, explicit person–company links, and CRM routes

Accepted 2026-11-05 for CRM-01/CRM-02 (PRD v2.5 §5A.4; companion PRD §5).

## Context

PR 01b established a workspace-scoped `contacts` identity with normalized, tenant-unique identifiers, an append-only consent ledger and controlled erasure. Erasure re-keys a contact and unlinks its `contact.*` audit history. The CRM needs organisations and relationships without a second contact or consent system and without weakening that erasure.

## Decision

1. **Companies** (`companies`) use the composite key `(tenant_id, id)`, a trimmed name (1–100), a generated `normalized_name` (trim, collapse whitespace, lower-case), an optional **normalized domain** and a description. The domain is a host without scheme, credentials, port, path or leading `www.`; IDNs are stored as punycode. A partial unique index on `(tenant_id, domain)` makes the domain the only hard company identity. The same domain may exist independently in another tenant. Names are never unique; same-name companies are surfaced as suggestions.
2. **Links** (`contact_company_links`) use the primary key `(tenant_id, contact_id, company_id)`. Separate composite foreign keys to `contacts(tenant_id,id)` and `companies(tenant_id,id)` make a cross-tenant link impossible even for the table owner. A link has an optional role (`title`), and a partial unique index allows at most one `is_primary` per person. The first link becomes primary. Unlinking the primary promotes the oldest remaining link. A trigger requires a live (non-erased) contact, locks it `FOR SHARE` to serialize against erasure, binds `created_by` to the verified transaction user, and makes link identity immutable.
3. **Optimistic concurrency**: `contacts.version` and `companies.version` start at 1. Every inline PATCH must send the version the editor saw. A mismatch returns 409 `{ reason: "stale" }` and changes nothing. The original full-replace `updateContact` service also increments the version.
4. **RLS and grants**: both tables enable and force RLS with the standard `app.tenant_id` policy. The runtime role gets `SELECT, INSERT` plus column-scoped `UPDATE` on companies (no DELETE). On links it gets `SELECT, INSERT, DELETE` and `UPDATE (title, is_primary)` only. Company deletion and archival are deferred.
5. **Erasure** (`erase_contact`, replaced in migration 0012) deletes the person's links before re-keying. Link mutations are audited as `contact.company_link`, `contact.company_link_update` and `contact.company_unlink`, targeting the contact, with metadata `{ companyId, fields }`. The existing definer therefore unlinks them like every other `contact.*` event, and the company's activity no longer shows the erased person. The company itself is kept.
6. **Audit and activity**: the CRM activity view reads the append-only `audit_logs`; it is not a second event store. Metadata holds field **names** and IDs only, never old or new personal values. Actor names resolve only for current members of the same workspace.
7. **Permissions**: `companies:read` (all roles) and `companies:write` (owner, admin, member) mirror the contact capabilities. Linking requires `contacts:write`. Viewers are read-only. Unknown roles fail closed.
8. **Routes**: the companion PRD names `/crm/people`, `/crm/people/:id`, `/crm/companies` and `/crm/companies/:id`. ADR 0003/0004 require private screens to live under `/workspaces/:tenantId/…` on the shared domain, with no tenant subdomains. The implemented routes are therefore `/workspaces/:tenantId/crm/people[/:id]` and `/workspaces/:tenantId/crm/companies[/:id]`. The older `/workspaces/:tenantId/contacts[/:id]` routes redirect there, preserving query parameters. The API keeps the established `/api/workspaces/:tenantId/…` prefix (`contacts`, `contacts/:id/companies[/:companyId]`, `contacts/:id/activity`, `companies`, `companies/:id`, `companies/:id/activity`) rather than the companion PRD's `/api/crm/...` sketch, for the same reason.

## Consequences

- No duplicate contact or consent tables. Consent history and erasure keep their existing contracts, and the erasure upgrade path is tested from a 0010 database.
- Name collisions never block work and never merge records. Domain and identifier collisions are explicit 409s that point at the existing record.
- Contacts still hold one email, phone and handle each (PR 01b constraint). Multiple identifiers per kind, merge, custom fields, saved views and company archival are later CRM slices.
- Migration 0011 is generated by drizzle-kit. Migration 0012 is hand-written (policies, grants, triggers, function). Adding the stored generated column rewrites `contacts` once; this is acceptable at current data volumes (no deployed customer data).
